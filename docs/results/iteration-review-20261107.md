# 多轮迭代仍出现问题的复盘

日期：2026-11-07。先保存、后分析；保存提交为 `0d86854`，运行代码仍为 0.28.7 / `2a7a422`。本次依据源码、提交历史、历轮失败报告和已保存的模型账本，未启动新的模型验收，也未操作服务器。

**主要判断：前几轮确实修复了缺陷，但跨阶段的业务要求没有足够早地固化成一致的程序契约和可重复的全过程验收。我们经常修通一个环节，随后才发现下一个环节仍会丢失权限、误解状态或阻止交付。真实模型的决策变化、验收器自身的错误，以及尚未完成的上下文成本治理，又放大了这种反复。**

这是对本次开发方法和实现的判断，不是把所有失败归因于 DSH、模型服务或用户要求。作为接手开发和监控验收的一方，我对覆盖不足、部分进度判断过早、验收驱动缺陷及额外复测成本负有责任。

## 1. 先分清“仍有问题”包含哪些情况

| 情况 | 本轮实际例子 | 应如何解释 |
| --- | --- | --- |
| 已修复问题在另一个环节表现相似 | 主人获准读群消息，材料仍在记忆校验或最终交付时被排除；DSH 能列目录，未实际读源码；读了源码，又解释错误 | 表面都是“不会用工具、消息隔离”，内部可能是不同断点。需要核查整条链，不能只确认入口成功 |
| 修复新引入的回归 | 从整体核验改为逐段核验后，正确的“材料不足，不能判断”也被拒绝 | 属于新增缺陷，不能称为外部服务不稳定 |
| 明确保留、尚未完成的项目 | 11 月 4 日按用户选择保留恢复续办缺口；当前长任务成本仍偏高 | 不能把当时的约定范围通过扩展成原整合方案全部完成，也不能把用户批准的暂缓当成开发免责 |
| 模型或平台调用异常 | 余额不足返回 402；最终观察中的模型请求返回 500；B站部分路径受限 | 区分账号、接口、请求与本地判断。500 的具体原因未定位，不能仅凭状态码认定与本地请求完全无关 |
| 验收方法造成的失败或误判 | 报告实际送达前 22 秒被驱动错误超时；只认特定函数名导致漏认真实源码读取 | 属于测试系统缺陷，需要修验收器，不能先改业务来迎合错误判据 |

当前证据支持：0.28.7 的既定本地故事和同进程连续两小时检查通过。它不支持“所有旧问题永久消失”“所有外部能力始终正常”“正常日常成本已达标”或“已完成真实 QQ 双向与真实群全流程”。真实主人私聊验证的是出站，群及 QQ 入站采用隔离回放，符合用户此前指定的边界。

## 2. 为什么修通一次，下一轮仍然失败

### 2.1 跨阶段的状态和权限没有形成完整契约

同一份工作同时涉及消息来源、会话范围、任务意图版本、活动计划版本、来源有效性、前台占用、依赖暂停、报告生成、核验和分段发送。每层都有合理检查，但早期没有把它们组合后的行为充分验证。

- 主人跨群查询：11 月 3 日发现核心已经放行，记忆来源校验仍拒绝跨群材料；11 月 4 日又发现最终交付阶段会丢掉任务中已经读到的群证据。读取权限正确，并不能自动证明后续表达材料正确。
- 巡视自等待：配置已经保存，来源任务未结束，调度器必须等待；设置任务却继续等首次巡视，形成“我等后台，后台等我结束”。此前状态只给出 active 和到期时间，模型无法从回执知道真正的阻塞条件。0.28.5 才补齐启动前提及等待原因。
- 原计划修改：测试首先覆盖了“新任务调整旧计划”。真实模型还会选择“修订原任务”，意图版本变化使旧来源失效；它随后取消旧计划再新建。任务结束了，但违反“沿用原计划”。0.28.6 才补齐这条分支。

对应源码：`packages/activity/src/service.ts` 的 `update/statusView`、`packages/activity/src/scheduler.ts` 的来源与前台占用判断、`packages/contracts/src/activity.ts` 的配置完成约定。问题不是应删除这些检查，而是必须让调用者取得一致、可执行的状态及下一步。

**开发上的缺口：业务要求已经写进方案，但没有同时变成接口回执、状态转移规则、跨模块测试和最终结果断言。**

### 2.2 测试数量增长，没有自动补齐模型行为和语义覆盖

498 项回归是有效的程序证据，但不同测试证明的事情不同。脚本模型可以确定地选择某条工具路径，不能代表真实模型会选择同样路径，也不能独立证明自然语言结论正确。

例如 `tests/sdk-fixture.ts` 的 `verificationResponse` 默认构造结构合法的通过回执，用于测试交付控制流；它没有阅读正文来判断事实。把这类测试通过解释成“报告事实核验可靠”，就超出了测试范围。计划测试缺少 amend 路径也是同类问题：已有测试并非没有价值，但漏掉的分支不会因其它几百项通过而获得保证。

近期真实运行才逐步揭示：列出工具不等于执行检查；执行检查不等于解释正确；报告通过结构检查不等于所有句子有依据；任务 completed 不等于满足“同一计划”等用户约束。

现有 `tests/group-patrol-amend.test.ts`、`tests/delivery-verification.test.ts` 等已补充这些回归。仍需把真实失败对应的脱敏场景及判据作为长期测试资产，而不是每次依靠现场人工发现相邻问题。

### 2.3 报告核验曾在漏检与误拒之间摇摆

11 月 7 日的变化能够直接说明这一点：

| 版本 | 真实观察 | 暴露的缺口 |
| --- | --- | --- |
| 0.28.3 | 把回复触发条件解释为缓存条件，从空缓存推断从未收件；整体核验通过 | 一个总的通过标记不足以覆盖所有断言 |
| 0.28.4 | 改为逐段、逐来源检查 | 改善漏检，但“事实、推断、意见、证据不足”的边界仍不完整 |
| 0.28.6 的真实观察 | 修稿已明确缺少独立材料、不下结论，仍因缺少独立材料被拒 | 新规则把合理的不确定声明当成需要额外证据的事实断言 |
| 0.28.7 | 区分证据不足、非事实表述和外部断言；最多三稿复用原材料 | 已校准已知失败与对照样本，仍不能证明所有自然语言都不会误判 |

逐段检查能保证模型没有漏报段落、没有捏造来源 ID，但“这份来源是否真的支持这句话”仍有模型判断。源码 `packages/memory/src/delivery-verification.ts` 明确体现了这一边界。合理方向是程序核对确定性事实和状态，模型判断确实需要语义理解的部分，并同时检查漏检和误拒；不是无限增加提示词或取消核验。

### 2.4 验收器也是程序，此前没有得到同等严格的维护

已记录的验收缺陷包括：

- 源码检查器只认几个函数名，漏掉实际已经读取的源码。
- 驱动自行使用 300 秒等待，而正式程序的生成、修订和核验阶段可以更长，导致实际交付前 22 秒误报失败。
- 原计划身份等约束核对太晚，出现阶段日志已宣布完成、最后读库才发现取消重建的情况。我当时也依据阶段日志过早报告过进展，随后才纠正。
- 私聊测试文案要求被测任务断言它未读取的服务器及发送范围事实，造成额外拒绝与重试；已改为只报告本任务能证明的结果。
- 校准和恢复探测的用量归属曾影响对账；模型账本、业务任务记录与验收统计需要独立核对。

当前完整驱动、真实核验回放及部分对账程序仍主要位于被 Git 忽略的 `.runtime/integrated-20261106/`，例如 `soak.mjs`、`audit-soak.mjs` 和 `replay-final-verifier.mjs`。公开仓库中有安装检查与程序测试，但只拉取仓库，不能直接复现本机整套真实验收。这是可复现性缺口。本次检查点保存了这些文件及摘要，但保存副本不等于完成脱敏、参数化和正式纳管。

**耗时中有可避免的部分：直到完整付费流程跑起来才发现小范围规则或驱动错误，随后修改、重新构建、重新计时。** 相同冻结版本连续两小时的要求是合理的；应减少进入该阶段前的漏检，而不是拼接失败时长或放宽通过条件。

### 2.5 上下文容量、运行速度和模型成本是三件事

此前主要解决了任务承接、容量一致性、结果丢失和中断。百万 token 上限允许任务装入更多材料，并不会自动让请求更精简。

代码核对结果：

- `packages/memory/src/index.ts` 未配置 compaction 时保留来源跟踪，并以 tracking-only 构建整理提供方。
- `packages/memory/src/compaction.ts` 在该模式下设置 `enabled:false`；`packages/core/src/compaction-runtime.ts` 跳过压力整理。验收运行状态也记录了 `not-configured`。
- 即便启用，现有策略主要按容量压力触发；默认阈值比例为 0.75。不能据此假定十几万输入、几十轮工具读取的任务会及时整理，更不能保证降低总成本。
- 轨迹索引和不可变事实缓存降低了一些本地 CPU 开销，但不等于减少交给模型的历史正文。

复核的用量如下，最终两小时包含在整段恢复工作内，两行不能相加：

| 范围 | 模型请求 | 已知累计 token |
| --- | ---: | ---: |
| 11 月 7 日恢复工作，含失败试跑、局部复验和主实例 | 959 | 47,381,635 |
| 最终两小时隔离观察 | 191 | 11,283,006 |
| 其中一个源码诊断任务 | 76 | 7,903,651 |

约 96.8% 的整段已知 token 来自隔离试跑和局部复验；源码诊断占最终轮约 70%。整段最大已计量输入为 186,281 token，并没有每次填满一百万。最终轮约 90.3% 为缓存读取；累计 token 不等于未缓存输入或账单金额，未知用量也不按零处理。

所以，开销主要由重复完整验收、较长的诊断工具链及反复输入历史共同造成。早先为赶截止压到一分钟的探索频率也放大了测试负载。不能把这些当成正常待机标准，也不能归咎于用户允许百万容量。后续应保留容量和无额外任务总量上限，改善材料组织、已读结果复用、工具查询粒度及无需模型的等待处理。

### 2.6 外部条件与本地判断混在一起，容易修错方向

用户浏览器已经登录但系统提示挑战，其中一次真实原因是页面推荐标题含“已验证账户”，被本地弱关键词判断误报。另一个弹幕失败是解析器未处理 Proto3 合法省略的零值字段。两者都是本地缺陷，登录或反复请求平台不能修好。

另一方面，登录有效确实不保证浏览器视频、HTTP 搜索、评论、字幕和媒体 CDN 都可用。应保留按账号与接口范围诊断，而不是把一次登录通过写成全部恢复。

最终两小时出现三次同一探索任务相关运行的 HTTP 500，轻量恢复探测成功后，较重接续请求仍可能失败。目前只能确认实际请求失败，未确定是提供方内部故障、特定请求触发，还是适配因素。它不构成所有本地代码无关的证明，也不能把轻量探测成功写成业务已恢复。

## 3. 两小时通过应怎样理解

最终 0.28.7 有真实的正向证据：指定对话完成、视频六帧及字幕有来源、DSH 实际读取并汇报、原计划身份保持、同任务恢复并分享、发送账本可核对、同进程连续运行两小时。

但审计程序检查的是这些指定场景、配置与进程连续性、已发生请求的对账等；它没有要求后续每个探索都成功，也没有正常日常成本的业务阈值。大部分请求发生在前 30 分钟，最后 45 分钟没有新模型请求；其中包含依赖异常后的等待，不能当作持续正常工作负载下的稳定性证明。

因此应保留原始通过结果，同时明确三个独立状态：

1. 既定功能场景及连续进程检查：通过。
2. 两小时内模型服务持续可用、所有新增探索完成：未证明，已有反例。
3. 日常成本及用户对自主性的满意程度：尚无足够证据给出达标结论。

本地主实例在上一轮验收期间仍按原配置关闭自主活动；启用活动的是隔离观察实例。不能用两者混合统计来判断日常活跃度。本轮不重新连接服务器，服务器状态沿用上一轮已保存的停止核对记录，不冒充本次新查。

## 4. 下一轮应改变的方法

| 优先项 | 应形成的产物 | 防止再次发生什么 |
| --- | --- | --- |
| 业务完成条件统一 | 每个真实诉求对应：输入、任务/计划身份、授权、实际工具结果、最终正文、平台回执、允许的未完成状态 | 接口成功或 completed 被当成用户目标完成 |
| 状态与阻塞原因统一 | 创建、修订、暂停、恢复、取消、交付各阶段的状态表和可操作回执；由程序提供当前状态事实 | 模型猜测后台情况、自等待、取消重建、重复探索 |
| 验收纳入版本管理 | 参数化驱动、脱敏对话及失败材料、通过/失败/误拒对照、验收器自身回归；账号和运行数据仍留在本机 | 同一报告下执行了不同的隐含判据，换机器无法复现 |
| 分层进入真实观察 | 先确定性回归，再局部真实模型复验，再完整原对话；全部通过后冻结包，运行两小时 | 为一个报告句子或计划分支反复重做整个昂贵业务 |
| 单独治理成本 | 固定同一业务样本，比较模型次数、每步输入、重复正文、缓存比例和有效交付；异常暂停单列 | 靠待机或服务故障制造“省 token”的假象 |
| 双向校准报告核验 | 程序直接核对 ID、版本、数量、读取覆盖和回执；语义核验同时检查漏检与误拒，修稿复用证据 | 越修越严导致有结果也发不出，或只检查格式却放过错误 |

这些是建议的后续实施顺序，本轮没有把它们写成已完成。无需推倒全部代码，也不能把“再补一些提示词、再加几项测试”当成足够的收敛办法。对已通过的能力保持回归，优先完成横跨模块的契约、可复现验收和上下文成本治理。
