## 3 交付缺口的确定性复现

场景使用真实 Host/SDK、合成群存储和脚本模型。先通过主人任务实际读取群消息，再在生成或核验阶段注入模型不可用。观察如下：

1. 业务 Run 已 `completed`，原结果引用及正文摘要仍在；`qq_browse` 只成功执行一次。
2. 结果交付进入 `rejected`，模拟结果渠道未收到正文。
3. 解除模型故障，再调用现有交付入口，返回原终止状态，不产生新的生成或核验调用。
4. 正常关闭并重启隔离 Host 后，状态与成果保留，但再次请求交付仍未接续。

对应 `native-delivery-interruption.test.ts` 和 `native-verification-interruption.test.ts` 的名称包含 `R1.1 known gap`。它们是现状刻画，不能计为 R06 修复验收。实现 R1.4 时必须把预期改成保留业务操作、只恢复受影响阶段并最终送达，同时增加取消、来源失效和未知副作用对照。

下一步恢复设计还须处理现有不可变材料、封存正文与交付有效期；不能只把 `rejected` 清回初始状态来满足测试。

脚本模型没有供应商 token 回执，上述 63 条请求的用量按未知记录，不能按零用量宣称降本；它们没有发往收费服务。DSH 结果归档测试不调用模型，因此没有对应模型基线。真实成本目标、预警值和节省比例均未确定。
