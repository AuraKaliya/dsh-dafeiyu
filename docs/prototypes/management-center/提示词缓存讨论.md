# 提示词缓存：代码事实与方案讨论

本轮仅修正原型并讨论方案，没有修改业务请求组装，也没有调用真实模型验证缓存。

## 先纠正原型的混淆

此前“身份基础与自我认识”被合成一个动态块，并排在首位。这不能准确反映当前代码。

| 材料 | 当前来源 | 变化特征 |
| --- | --- | --- |
| 初始化身份底色 | `Autobiography.foundation()` 首次导入后保存在 `memory_seed` | 当前实现中实例内稳定；后续读取已有值，不重新导入模板 |
| 当前自我认识 | `memory_self_revisions`，经 `PersonaRuntime` 投影 | 真正修订或撤下时变化；不是初始底色的一部分 |
| 召回、同群背景、任务状态 | 各上下文贡献者 | 随输入、执行状态及来源范围变化 |

`packages/core/src/index.ts` 的 `persona()` 返回 `foundationMemory`。`conversation-coordinator.ts` 将它直接交给 `runtime.run`；`runtime.ts` 将其文本注册为 order 0 的 `dafeiyu-persona`。因此当前靠前的文本不是每轮重新生成的自我认识。

源码依据：

- `packages/memory/src/autobiography.ts` 的 `foundation`、`projected`、`prepare`。
- `packages/core/src/index.ts` 的 `bindExperienceMemory`、`persona`。
- `packages/core/src/conversation-coordinator.ts` 的受理和 runtime 调用。
- `packages/core/src/runtime.ts` 的 systemPrompt 注册。
- `packages/core/src/persona-runtime.ts` 的记忆条目选择与投影。

原型已拆开这两类内容。底色正文只有连接实例后才能只读展示，本原型不把模板或虚构文字冒充当前实例的记忆内容。

## 真正需要检查的是完整前缀

DeepSeek 官方 API 文档说明，复用依赖已经持久化且完全匹配的前缀单元；仅存在一段共同文本，不保证某次请求立即命中。系统还会识别公共前缀，缓存是 best effort。官方材料与来源记录保存在 `../../references/prompt-cache/`。

这个官方 API 说明是机制参考，不能直接假定 DSH 账号线路的全部序列化和计费字段与之完全相同。实际结果以该模型线路的用量回执为准。

“动态在前”通常缩短可复用前缀，不等于一定完全无法命中。下面只是结构示意，不是供应商 Token 编码：

```text
不利于历史复用：S + C1 + H
下一次变为：    S + C2 + H
共同部分可能只剩 S；后面的 H 虽相同，也不再是相同前缀。

目标结构：      S + H + 本轮新增内容
下一次：        S + H + 已提交的新内容 + 下一轮新增内容
```

S 表示稳定内容，H 表示同一会话已提交且仍合法的历史。tools 是独立字段，其最终编码位置必须在适配器/模型线路层面核验，不能用 JSON 字段顺序或 UI 排序推断。

## 当前代码里更值得优化的地方

1. DSH `RuntimeContextProjection` 已做到内容不变时不追加，变化时产生新快照。部分模型线路还支持 systemPrompt 的 in-history 更新，但这是有条件的，不应当成所有路由的保证。
2. 大肥鱼 `ContextRuntime.retire()` 与 `retireContextCarrier()` 会把旧上下文载体从早先 surface 位置替换出去。这样做保护了来源与当前性，但普通状态变化也可能改变较早的消息，从那个位置打断历史前缀复用。
3. Core 已使用稳定 JSON 与工具名称排序，不必重新发明另一套排序。需要保证之后加入的状态字段、更新时间或随机 ID 不无故改变稳定区。

有关历史替换的判断来自代码结构，还没有测量真实请求中的最长公共前缀或缓存命中比例。

## 建议方案

### 稳定规则与实例稳定内容

公共工作原则、数据与指令边界、当前场景固定规则形成稳定部分。初始化底色作为实例稳定内容单独保留，仍由记忆模块拥有；稳定不等于重新用模板覆盖成长。

工具定义保持实际授权下的稳定顺序和内容。插件或权限改变时必须更新，不能为了缓存固定一套已经越权的工具。

### 历史前缀尽量只追加

同一会话中的已提交、仍允许使用的历史保持原文和次序。普通状态更新追加新的**完整上下文快照**，不回写早先快照；内容未变化时不重复追加。这里不擅自改成差量协议，因为 DSH 的 snapshot 语义需要完整当前视图。

当前自我认识仍在记忆真正变化后生效，不为了缓存延迟成长。它作为新的状态快照出现，不并入每轮重写的首条 system 文本。旧版本若保留，只能作为带版本的历史事实，不能继续充当当前状态或权限。

### 必须允许的失效

资料撤回、隐私范围变化、权限失效、必要压缩和模型路由变化，应按正确性要求清理或重建请求。不能为了命中率把失效或不允许读取的材料继续发给模型。

因此正式调整前需要区分：普通状态更新、可作为历史保留的旧版本、必须撤回的材料。不能直接删掉 retire/guard 检查。

### 有边界的压缩

追加快照会增长历史。达到明确的上下文阈值后进行压缩并开启新的请求前缀阶段，接受这次必要的缓存变化；不为了维持缓存无限保留历史。

## 如何确认有效

先做短的本机结构检查：固定内容不变时确认序列化后的稳定区一致；普通对话/工具步骤保持历史前缀；记忆更新只增加合适的新快照；撤回时仍正确排除材料。只记录摘要、变更原因和范围，不保存模型内部推理。

真实缓存效果需要单独观察模型返回的缓存/未缓存输入用量。不能凭“预览里静态在前”宣布缓存已优化，也不保证第一次请求或每次变化请求立即命中。本轮没有做真实模型测试。

## 原型的两种查看方式

- **当前代码 · 逻辑分层**：把稳定底色和动态自我认识分开，避免再次误导。
- **缓存优化草案 · 待讨论**：展示稳定部分、合法历史、本轮新增内容的职责关系。它不是已经实施的后端排序。

本方案继续使用 DSH 的 Agent/Session/Tools 循环，不建立另一套模型循环；接口变更在正式开发时统一调整，不引入兼容分支。
