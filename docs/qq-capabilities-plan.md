# 第二阶段：QQ文字能力与流程整合开发方案

版本：1.0；日期：2026-10-25；基线：`384cffd`（功能基线 `fda28fd`）。这是统一架构中的阶段2，不是早期 `phase-2-plan.md` 的接入试验。依据总方案、人格成长方案以及用户将最终验收延后到整体开发完成的决定编写。

## 1. 目标与范围

QQ提供消息渠道和可调用能力，大肥鱼决定浏览、选择记忆及如何完成任务。渠道不维护另一套人格、兴趣或模型循环。首要结果是：新入口可装配QQ；文字称呼、群范围变化、浏览、选择观察与任务结果交付都有明确来源、状态和恢复规则。

本阶段不开发QQ图片／语音／文件内容理解、B站、自动活动日程、记忆E自动归纳，不连接服务器。被动缓存和运行记录不等于长期记忆；普通群消息不自动唤醒模型，也不自动写入阶段人格。测试使用虚构账号、脚本模型、真实本地DSH和SQLite以及回环OneBot替身。真实模型、真实平台、人工语义和资源联合验收全部留待整体开发完成，不能把替身发送记作真实QQ发送。

依赖方向：Host→core／memory／timeline／QQ；QQ→core提供的授权、事件、任务、交付及观察端口；core→契约中的provider，不导入QQ；memory管理持久记忆及来源，不能反向导入QQ。自然称呼、群同步与普通回复只依赖core，关闭memory时仍能聊天；启用选择记忆或原生任务时，Host必须检查相应provider与policy存在，缺少时不能宣称能力可用。activity和媒体是将来的调用者／服务，不作为本阶段启动依赖。

渠道保持 `qq + botId` 唯一。能力使用独立扩展身份 `qq-capabilities`，动作通过v3注册，最初只暴露读取及受控本地贡献；不得提供任意目标、任意正文的通用发送工具。v2渠道在转换完成前可与独立v3能力并存；同名动作、重复渠道／账号和失效授权仍拒绝。关闭先停准入和计时器，再排空动作／发送，最后卸载provider并关闭库。

## 4. 配置和渠道行为

旧配置继续合法；新增字段均有兼容默认值。`naturalNames`是显式名称数组，默认空数组以避免旧群突然增加触发；新模板建议配置“大肥鱼”“蓝色大肥鱼”。只匹配正文中直接称呼的位置，不检查引用正文、昵称、卡片、图片、转发或JSON字符串中的名字。实际at与引用本人的已缓存消息仍有效。自然称呼不授予主人权限。

自然称呼先支持句首（可有空白或中文呼唤标点）及显式文字 `@名称` 的独立称呼；紧随标点、空白、结尾或常用请求引导词。名称中间出现、名字作为另一词的前缀、代码／引用块不按自然称呼触发。解析函数单独测试；不调用模型分类所有群消息。当前未接入的媒体继续给出已接收但未读取的说明。

新增 `groupSync`：`enabled`默认false；`mode`为`allowlist`（默认）或`joined`；间隔默认30秒，最小5秒；`maxStaleMs`默认120秒，不能小于间隔。joined必须显式开启同步，表示本地profile授权开放已加入的群。allowlist启用同步后有效范围是配置groupIds与最新已加入群的交集；未启用同步保留旧静态行为。不要从管理中心线上“所有群开放”的历史推断本仓库也得到相同配置。

启动完成账号核验后获取 `get_group_list`，后台单一计时器串行刷新，不重叠、不高速重试；每次刷新前验证账号。首次失败没有有效动态群范围；后续失败可在明确的陈旧期内保留最后成功集合，超过期限拒绝新的群读取／接收／发送。成功得到空列表意味着无已加入群。离开的群立即失去新访问资格；私聊仍只允许配置ownerId。重开后的旧快照只作历史状态，不在新账号核验和成功刷新前用作动态授权。

状态提供配置群、最新已加入群、有效群、同步是否启用、最后成功时间、是否陈旧与稳定错误码。状态／日志不包含token或平台错误原文。群名仅为显示材料，不能改变权限。每次实际发送前再次核验目标和账号；同步、动作与发信都接入统一关闭信号。

## 5. 浏览、观察和记忆接口

拟定动作：`qq_groups`（查看有权限的群及同步覆盖）、`qq_browse`（有界读取缓存）、`qq_observe_select`（对实际曝光快照选择none／原文／片段／摘要）。所有入参严格校验；游标绑定账号、会话、查询边界与版本，不可跨范围借用。

本阶段browse首版只读**插件实际收到并缓存的内容**，不承诺补齐离线历史或平台全量记录。每次最多20条、正文总体预算不超过观察契约；带消息ID、发送者、可核验时间（旧缓存缺失时为unknown）、缓存水位、截断／缺口、媒体未读取说明。缓存丢弃旧消息后不能说已永久保存；原始材料是否再次可读必须明确。继续分页由大肥鱼决定，没有每轮调用次数上限。

Conversation动作仅能读核心签发的当前QQ会话；私聊不能因owner身份自动读取所有群，更不能把私聊正文通过群动作带出。native Task动作需实际任务来源授权／范围白名单及memory端口；`groupId`只是资源请求，不是授权凭据。无native授权端口时动作明确不可用，不能编造一个群消息作为入口。跨场景检索保留D1授权，不将平台加入资格等同记忆出口权限。

先落实际曝光事实与范围受限的来源快照，再让大肥鱼选择是否长期贡献。选择none只保存必要活动事实；原文／片段需精确对应来源版本；摘要继承全部实际输入限制（包括历史影响），不能仅按最终引用降级范围。请求ID按Run／operation／批次绑定；快照内容不能由模型回传替换。使用memory的已有观察与贡献接口，必要的v3会话适配放core完成，不让QQ自行构造可信authority。候选人格由memory阶段E处理，QQ不自动采用人格。

平台撤回事件或明确刷新发现变化时，缓存和观察来源推进版本／失效；离线未获知的撤回不保证实时发现。逻辑失效先于异步清理，恢复不能复活旧摘要／凭据。关闭或卸载后上下文授权和观察选择票据失效。

## 6. 分段与任务交付接口

### 6.1 传输与分段

沿用平台单段最多4000字符的开发限制；按Unicode代码点／代理对完整边界切分，优先换行，输出不得丢字或重复。分段标题若采用，必须算入限制且区分正文／渠道附加说明；先实现不改写正文的分段。总正文最大32000字符作为资源边界，不是工具次数限制。

发送前持久化 `replyId + route + anchor + bodyHash + segments + planHash`。相同ID异文／异目标冲突；每段先落sending，再实际发送，确认后记录平台messageId。全成功才为sent，已确认部分与未发送部分明确返回；任一unknown禁止自动续发／重放。进程重启把sending视为unknown，绝不通过猜测receipt变成成功；明确尚未调用平台的段可在有效源授权下继续，同一reply并发只能有一个发送者。旧单回执仍视为完整sent，不能重新分段发送。

每段发送前检查账号、群范围、取消信号和交付凭据；检查失败在尚未发任何段时为not-sent，已有段时必须记录partial。core对外的旧DeliveryResult保守映射unknown，不能把部分发送映射成可盲重试的not-sent；细节在QQ账本和状态可查。新任务状态另列partial／uncertain。仅在关闭后读取状态不应唤醒模型或发请求。

### 6.2 新任务流

新增core可信消息受理端口，绑定Journal inboundId、实际发送者、扩展身份、范围、授权policy和输入版本，给QQ动作调用。模型可提出任务目标，但不能填sender／producer／owner来授予权限。明确任务、探索兴趣、普通观点和引用中的命令分开保存；普通对话不强制建Task。主人身份由入站envelope核验，群显示名相同不算主人；非主人可聊天但本阶段不获得主人跨场景任务权限。

Task使用现有repository、Run、epoch、TaskIntent及检查点。请求幂等，失败和等待可查；用户取消／目标变更经core使旧Run与结果失效，非阻断异议不暗改目标。无消息任务与聊天任务共享动作能力，origin与motivation保持独立。

新v3交付锚点为reply或task-result。reply保持inboundId；task-result绑定taskId、请求来源、目标会话、intentVersion、授权版本和有效期。proactive锚点留给阶段4，不在本阶段开放。新群闲聊不使任务结果失效；目标变更、取消、来源删除、出口权限收紧或过期会失效。v2仍保持D3“模拟且最新消息”的语义和测试，不通过修改一个flag宣布已支持新任务。

任务内部结果→memory表达策略／D2限定材料→干净的目标人格会话整理→独立忠实性校验→再次检查来源／epoch／范围→固定正文凭据→QQ分段发送。整理与验证仍使用DSH，不直接转发执行报告；不将所有内部私有证据注入目标会话。异常保持可核验状态，不以模型说“已经发了”计成功。需要扩展D2锚点与持久表时先使用增量schema及旧数据样本验证，不复用旧inboundId唯一约束承载多个不同任务。

## 7. 数据迁移与兼容

2A把QQ库从严格识别的v0升级到v1，application_id为 `0x44465131`。已有messages／receipts／handled列、行、主键及顺序不变；本步只增加迁移标识。旧库必须确认为三张已知表的完整结构，拒绝未知／不完整／未来版本、额外业务表以及伪装应用ID。只读预检不建表、不改journal mode。新库构造可初始化；旧库必须显式 `migrate`，managed入口只有Host的备份迁移流程可升级。普通启动报MIGRATION_REQUIRED，不静默改旧库。

2B新增v2群快照表；2C将新增消息元信息／观察快照，不回填虚构时间；2D再新增分段计划／逐段回执，2E新交付账本使用独立v3表／版本。每个步骤给出实际schema目标及迁移报告，未实施表不提前存在。旧messages缓存只在原规则内逐渐淘汰，handled和成功回执不得被清空。

Host同步QQ目标版本、完整结构识别及迁移引擎指纹（包含QQ迁移代码）。旧库先只读计划→SQLite一致性备份→关闭准入后的逐库增量升级→校验原行哈希→完成标记；中断按同一计划前进恢复，不从备份覆盖新数据。未知库在任何写入前拒绝。profile／memory／runtime／DSH会话不随QQ升级重置。

旧0.3.0代码没有QQ版本检查，不能保证它会拒绝新库；**禁止把升级后的库交给旧二进制写入**。需要回退时停止所有写者、使用与schema兼容的代码前进修复；仅在新库没有任何新状态时，才能另行讨论恢复迁移前副本，不在开发脚本中自动回滚。此限制必须如实记录，不能虚称旧代码具备未实现的拒绝保护。
