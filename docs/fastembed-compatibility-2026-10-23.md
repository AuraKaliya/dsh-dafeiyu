# 现有 FastEmbed＋ONNX 服务的本机兼容验证与资源方案

日期：2026-10-23（北京时间）。结论：**现有BGE服务可以作为新记忆插件的复用对象；本机同源复现的接口与召回验证通过。新索引固定使用ONNX profile，不能直接混用原PyTorch向量。**

本轮完成的是本机验证，不是服务器部署验收。服务器只接受源码、包版本和模型指纹的只读核查，没有推理请求、配置修改、进程重启或缓存访问。

## 1. 已核实的实际契约

| 项目 | 服务器现状及本机复现 |
|---|---|
| 模型 | BAAI/bge-small-zh-v1.5，512维 |
| ONNX来源 | Qdrant/bge-small-zh-v1.5，revision `46fbe35fd4374a00fee7de77dfddaeb6dd6a2c59` |
| 模型文件 | model_optimized.onnx，94,781,076字节；SHA256 `1294ea4b6331115a353d81f96b85e8c8d7fdcc284453d5b2fab5b016230aad38` |
| 文件一致性 | ONNX及6个模型／分词配置文件，共7个文件，逐文件SHA256与服务器相同 |
| 运行时 | FastEmbed 0.9.0、ONNX Runtime 1.31.0、tokenizers 0.23.3、NumPy 2.5.4；其他已检查服务包也匹配 |
| 计算方式 | CPUExecutionProvider，threads=1，parallel=None，一份模型、推理锁串行化 |
| 服务接口 | POST /v1/embeddings；模型名称必须匹配；字符串或字符串数组；float或base64输出 |
| 输入限制 | 最多8条／请求，每条最多6000字符，总计最多24000字符，请求体声明长度上限512KiB；分词后实际截断到512 token |
| 查询指令 | 服务本身不自动加指令，只对收到的文本调用 model.embed；查询／文档角色由调用方决定 |
| 池化与归一化 | 已核查FastEmbed关键源码：三维输出取首token，二维输出直接使用，然后归一化；本机结果范数误差小于1e-4 |
| 缓存层 | 6191转发到6190；现有键使用模型名称＋文本，未包含完整运行profile |

服务代码快照与服务器原文件SHA256相同；已检查的4份FastEmbed关键源码文件也与本机安装版相同。原服务的公开程序代码保存在评测reference中，仅用于本机验收，不是覆盖服务器的部署包。

包名、模型名和维度相同本身不足以证明向量兼容，因此另外验证了文件指纹、输入指令、数值输出和检索效果。未复制真实记忆、缓存数据库、登录态或凭据。

## 2. 评测条件

- 继续使用上一轮冻结的100条虚构中文记忆与47个查询，43个有答案、4个无答案；未修改标签。
- 同一台本机Ryzen 9 9950X3D，约31.2GiB物理内存；CPU单推理线程，无Torch、无CUDA依赖。
- 两组独立进程：raw为查询原样输入；prefixed为客户端添加 `为这个句子生成表示以用于检索相关文章：`。文档均原样输入。
- 通过FastAPI TestClient在本机进程内执行原服务的ASGI路由及真实模型，不启动网络监听。时延包含ASGI和JSON开销，不含TCP、服务器调度或真实DSH链路。
- 文档批量8；单查询预热后重复3轮，固定随机顺序。没有模型下载或其他模型评测同时运行。
- 压力阶段：20批、每批8条、每条约1000个汉字，实际由模型截断到512 token。压力阶段不计算召回质量。
- 记录20ms采样工作集和private内存，并读取Windows进程RSS及commit高水位，避免只用瞬时工作集推断峰值。

## 3. 召回结果

| 方案 | Hit@1 | Recall@5 | MRR@10 |
|---|---:|---:|---:|
| ONNX原样查询 | 69.77% | 95.35% | 0.8256 |
| ONNX客户端加查询前缀 | 74.42% | 95.35% | 0.8450 |
| ONNX原样查询＋BM25，RRF k=60 | 74.42% | 95.35% | 0.8457 |
| ONNX加查询前缀＋BM25，RRF k=60 | 79.07% | 95.35% | 0.8651 |
| 上轮PyTorch BGE，查询加前缀 | 74.42% | 95.35% | 0.8450 |

加前缀后的ONNX结果与上轮BGE的上述指标一致。前缀改善第一条排序，Top-5覆盖不变。保留原有两道漏召回案例和样本规模限制，不将同一数据集上的复测当作新增独立评测样本。

选择：新记忆插件采用**查询端添加一次前缀、文档端不加前缀**。服务端无需为此修改。防止查询被重复加前缀，profile必须明确记录双方职责。

## 4. 内存与性能

| 指标 | 原样查询 | 客户端加前缀 |
|---|---:|---:|
| 单查询ASGI请求P50 | 5.93 ms | 8.14 ms |
| 单查询ASGI请求P95 | 7.12 ms | 9.33 ms |
| 100条文档编码 | 0.463 s | 0.467 s |
| 文档编码吞吐 | 216.0条/s | 214.0条/s |
| 正常短文阶段OS峰值RSS | 231.05 MiB | 231.26 MiB |
| 正常阶段末RSS／private | 211.23／188.24 MiB | 211.36／188.52 MiB |
| 长输入压力OS峰值RSS | 407.36 MiB | 407.66 MiB |
| 长输入压力OS峰值commit | 438.36 MiB | 438.91 MiB |
| 长输入每批8条请求P50 | 589.10 ms | 584.31 ms |

压力后内存没有立即回落到短文本水平，部署预算按高水位保留，不能按约211MiB常态值规划全部余量。

相比原PyTorch评测约688MiB进程RSS峰值，本次正常ASGI链路RSS峰值约231MiB，但运行时、线程数、计时边界不同，不应把两轮时延直接解释为纯模型速度比较。本轮压力峰值也不证明所有输入、并发或长期运行情况下的绝对上限。

## 5. 接口与数值验证

已通过：512维、有限数值、输出顺序、L2范数、单条与批量一致性、float与base64一致性、字符串与数组输入一致性、usage计数、健康状态，以及9类错误请求。

错误请求包括空数组、空白字符串、错误模型、错误维度、超过8条、单条字符超限、总字符超限、不支持的编码格式和声明请求体过大；返回对应400／422／413状态。

同源FastEmbed直接调用与ASGI输出最大绝对差为0；单条与批量最大绝对差为0。范数误差约1.19e-7。以上是本次虚构样本的结果，不是跨硬件字节一致性的永久保证。

### 长文本边界

两条共享约800汉字前缀、结尾分别为“允许发布”和“禁止发布”的输入，返回向量完全相同；usage合计1024，说明每条只保留512 token。HTTP字符上限和模型token上限是两回事。

因此新插件必须在调用前按相同分词器检查并切片：文档按语义边界拆分并保留来源位置；查询超过包括指令在内的输入预算时明确处理，不能静默截断后声称检索覆盖完整问题。分片器尚未实现，不以这次边界观察冒充已修复。

### 与PyTorch向量的关系

对相同100条文档及47个查询重新计算PyTorch向量，与ONNX结果比较：

- 文档最大逐元素绝对差约3.01e-4。
- 加前缀查询最大差约2.68e-4。
- 各组最小余弦相似度均高于0.9999987。
- 没有通过1e-5的逐元素严格等价检查，尽管本测试集检索指标一致。

结论为：**本轮语义召回表现一致、数值非常接近，不能宣称字节或严格数值可互换。** 新建ONNX profile和索引世代，重新生成此前仅用于评测的PyTorch向量；不直接混用。其他真实历史向量未读取，也未验收复用。

## 6. 复用接入方案

1. 新插件复用现有6190推理服务，不新增模型实例；当前6191缓存层和已有调用方保持不变。
2. 新插件先维护自己的持久化向量／结果缓存，键绑定完整profile、文本哈希、查询／文档角色；可见范围和删除状态仍由记忆服务在读取时检查。
3. 不将6191现有“模型名称＋文本”的键当作profile版本证明。后续若要共用其缓存，应另行设计版本命名空间并验收；本轮不改缓存、不清空旧索引。
4. 固定ONNX文件、分词文件、FastEmbed／ORT版本、池化、归一化、前缀和512维。部署前再次核对指纹；变化后停止复用旧profile并构建新索引世代。
5. 当前健康接口只报告模型名和维度，不提供全部指纹。因此HTTP健康正常不能单独充当profile一致性证明；部署预检负责指纹核对。
6. 客户端限单推理并发，每批不超过8条，长片段可用更小批量；后台建库分批让出执行机会，避免阻塞交互检索。不增加每轮工具调用次数上限。
7. 服务不可用时降级到关键词和关系检索，明确标记语义召回不可用；禁止自动下载另一份模型或转发真实材料到未配置的外部服务。

## 7. 4GB服务器上的2GB规划预算

用户已确认服务器总内存4GB。2GB是当前保守的开发／部署规划预算，后续用户会根据实际表现调整；不是物理总内存声明，也不是现成空闲内存。

工程验收暂按不超过2,000,000,000字节规划本方案运行组合。下表为预算目标，尚未作为系统资源限制部署：

| 分项 | 初始预算目标 | 说明 |
|---|---:|---|
| 共享embedding服务 | 512 MiB | 只计算一份；本机压力commit约439MiB，仍需实际组合测量 |
| 记忆协调、分析任务容器、索引／数据库缓存 | 384 MiB | 待实现验证；不在本机另起大语言模型；不能无界驻留向量和原文 |
| 剩余组合开销与余量 | 约1011 MiB | 留给DSH协同上下文及必要余量；不是已测空闲值 |

操作系统、QQ及其他程序的既有占用还需与4GB整机一起核算，不能用上述分配证明整个服务器可稳定运行。共享服务已在运行，规划时不能把既有占用和新增占用重复计算。

具体策略：单实例推理、单并发、增量向量化、磁盘持久索引、限制内存缓存、限制工作状态和候选体积、后台任务分批。长输入压力后的分配器高水位应计入预算；暂不自动重启服务释放内存。

未来真实接入前需要组合验收：空闲基线、加载、增量建库、交互检索、压缩和后台整理重叠，记录RSS、commit、系统空闲、换页及延迟。若余量不足，先缩减批量和缓存、错开后台任务；不默认调整用户服务器内存或现有程序。

## 8. 交付与仍待验证项

本机完成两种查询模式、接口契约、长输入压力和跨运行时向量比较。既有100条样本冻结；全部推理发生在本机，没有调用服务器在线embedding接口做推理。

尚未完成：生产插件适配、长文分片器、真实调用方完整路由检查、现有缓存升级、2GB受限整机组合测试、服务器端性能测试。现有服务的本机同源复现不能替代这些验收。
