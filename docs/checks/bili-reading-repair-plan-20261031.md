## 1. 必须完成的结果

1. 正常任务能够完成、等待、取消或失败，不遗留没有执行器的 `running` 状态。

5. 阅读进度与结论按任务隔离，程序事实有实际操作和来源支撑。
6. 长任务在执行过程中形成检查点并切换工作上下文，累计消耗可以增长，单次请求上下文保持在设定预算内。

## 3. 先统一契约

### 3.1 浏览器请求与结果

将 `BiliBrowserRequestSchema` 按 `section` 拆为判别联合：发现、搜索、视频信息、评论、单帧、批量帧各自声明必要参数。服务端工具、客户端和浏览器桥接复用这些契约，移除各层重复维护且上限不同的定义。

新增公共目标解析函数，用于生成目标 URL、校验最终页面和解释可接受的重定向。搜索校验关键词、排序、页码；视频校验 BV、AV 的已验证对应关系和分 P。校验规范化后的业务字段，不依赖 URL 字符串逐字相同，也不能只检查域名。

结果明确区分 `success`、`empty`、`partial`、`unavailable`。没有更多结果、没有可见评论、尚未加载、网络失败分别表达。浏览器不支持的排序或字段必须在覆盖说明中标明。

### 3.2 批量帧契约

每个请求时间点必须对应一条结果，包括未执行的剩余点：

```ts
type FramePointResult =
  | { status: 'ready'; requestedMs: number; actualMs: number;
      source: MediaProviderRef; contentHash: string }
  | { status: 'failed' | 'not-attempted'; requestedMs: number;
      errorCode: string; retryable: boolean };
```

批次另带 `batchId`、视频身份、CID/分 P、视频时长和覆盖说明。时间点按请求关联，允许内部排序采样，但不能把结果顺序变化误认为相同采样。

工具交互采用下面的形式，保留现有 `requestId`：

```text
bili_frames({bvid, pointsMs})
  → 每帧 source 引用、实际时间点与状态

dafeiyu_media_read({mode: "images", sources: [...]})
  → 一次视觉分析，逐帧关联观察结果
```

媒体多图入口可兼容已获取的 `assets`，但 `sources` 与 `assets` 必须二选一。模型不需要把 sourceKey 猜成 asset，也不需要逐帧调用获取工具。

### 3.3 阅读记录

复用 `biliOwner(context)` 所代表的任务范围与任务版本，将主键改为 `(owner, bvid)`。分 P、字幕轨和帧各自保存 CID 等身份。所有查询、索引、更新、删除或失效操作都必须提供当前任务范围。

分开保存两类内容：

- 程序事实：实际取得和曝光的材料、字幕区间、评论游标、实际采样帧、失败状态、来源版本。
- 模型判断：结论、疑问、值得保留的观察、下一步建议。

`bili_reading_save` 只提交判断和结束/继续意向；已经读取了什么由实际回执生成。首次建立记录也必须绑定已经观察到的视频来源。不存在或越界的来源不能写成阅读事实。

保存采用版本校验与幂等键。同一保存请求返回同一记录版本和检查点；重复保存同一视频不增加“完成了几个阅读单元”的计数。

### 3.4 任务阶段与执行结果

在 `TaskExecutionFrame` 中显式传入 `toolStage` 和阅读工作单元引用。阶段来自经协调器验证的执行计划；模型可以提出阶段切换意向，程序仅在当前任务权限内执行。

任务运行结果使用判别联合区分最终结果、等待和内部接续。内部接续不伪装成模型最终回答：

```text
final(resultRef)
wait(checkpointRef, reason)
segment-yield(checkpointRef, reason)
```

## 4. A包：修复任务收尾与交付状态

涉及 `execution-coordinator.ts`、`runtime-store.ts`、`execution-frame.ts` 及任务交付投影。

先撤下当前未经集成验证的自动续段接线，恢复原有完成与等待路径；保留纯判定策略，等 F 包完成后再启用新接线。

收尾必须是一个互斥的状态判定，优先处理取消/中断，再处理等待、内部接续和正常完成：

| 情况 | 程序动作 |
|---|---|
| 正常返回，未请求等待或接续 | 完成任务运行，进入已有最终交付流程 |
| 明确等待或存在阻断事项 | 写等待状态及检查点，不再调用完成路径 |
| 内部要求切段 | 交接到下一段，保持任务进行中 |
| 取消或失败 | 保留实际进度，执行对应既有状态转换 |
| 检查点或接续落盘失败 | 记录具体失败，进入可恢复状态，不能吞异常后宣称完成 |

新增内部终态 `continued` 表示该 run 已交接。它释放本段调度名额，但不产生最终回答，不进入最终交付候选查询。界面按任务根展示“执行中/接续中”，不要把每段显示为新的用户任务。

`continued` 的引入须更新运行存储版本与所有状态消费点，包括恢复、任务状态查询、执行日志、结果选择和交付。未显式填写 `complete` 的正常最终回答仍可按既有规则完成，不能因缺少这个字段而挂起。

验收使用真实协调器与 RuntimeStore：正常完成、等待、无阅读检查点、已有检查点但不续段、续段失败、取消和异常各有明确结果；不存在已经离开执行器却仍标记 `running` 的记录。

## 5. B包：任务阅读记录与显式升级

涉及 B站 store、storage-status、Host 存储预检与安装初始化。

### 5.1 数据布局

阅读状态使用任务范围主键，保存记录版本、程序来源、判断和检查点引用。有界索引只查询当前任务的最近记录与重点记录。总数使用计数查询，最近记录使用带索引的 `LIMIT`，不先加载整张表再截取。

公开视频内容和任务阅读状态分别存储。公开内容可以复用缓存；跨任务使用时创建本任务的观察引用，不直接沿用别的任务的进度、结论或权限。

### 5.2 迁移路径

B站目标存储计划升至 v4，支持：

- v2 → v4：保留全部原始页面、来源、媒体、诊断暂停与请求记录，创建任务范围阅读表。
- v3 → v4：保留旧阅读记录。旧记录没有可信任务归属的，进入遗留记录存储，不自动分配给任意任务，也不进入当前任务工作视图。
- 新安装：直接建立完整 v4 结构。

运行存储为 `continued` 与持久接续记录建立独立的版本升级。最终版本号由实现时的完整存储契约确定，不通过忽略版本检查实现兼容。

### 5.3 升级顺序

1. 只读检查 application_id、已知旧版结构、数据库完整性、agent/profile 身份及运行占用。
2. 预检返回“当前可用 / 已知可升级 / 不支持 / 身份不符”等不同状态。身份核验不能因为版本较旧就一律判失败。
3. 在实例停止、存储占用锁取得后生成一致性备份；包含相关数据库、配置和版本清单。
4. 使用显式迁移器执行事务迁移。迁移前后均核对身份、结构和保留数据数量。
5. 重新执行当前版本预检，再启动实例。

移除 BiliStore 构造器里的隐式写库迁移。身份错误、未知版本、结构异常均在任何写入之前失败。多库升级中途失败时保持实例停止并记录已完成步骤；不得以混合版本继续启动。

验收覆盖 v2/v3 升级、新建库、错误身份、错误 application_id、中途失败与重复运行迁移器。错误身份路径不得改变原数据库。

## 6. C包：搜索与评论入口贯通

涉及 `bilibili/service.ts`、`client.ts`、`pages.ts`、`plugin/bili-browser.ts` 和共享契约。

搜索继续支持当前任务中的正常关键词，保留长度与输入检查，不恢复固定句式或字符偏移要求。

客户端按请求 section 校验目标，搜索结果不再经过视频 URL 分支。客户端、浏览器桥接、服务层分别校验各自职责，使用同一目标规则避免再次分叉。

通道选择由程序处理：查询已知状态后使用可用路径。已暂停的路径在条件变化前不再反复尝试；临时失败的有限重试由适配器完成。明确的账号、验证挑战或权限失败不通过换路径无限重试。

搜索和推荐统一输出逐条候选，包括 BV、标题、作者、发布时间、播放量、时长与来源引用；无法取得的字段为未知。浏览器推荐也登记逐条标题，修正仅登记“首页推荐”总标题的问题。

页码、每页数量、nextPage 上限使用同一契约。达到本地分页限制与平台确实没有更多结果分开表达。

评论输入和输出采用同一游标协议。现有 `seen` 输入 200 条、输出可达 500 条的差异应消除；去重集合优先保存在后端，模型携带短游标。浏览器按可取得的评论 ID、根评论与父评论组织数据；拿不到稳定 ID 时保留明确缺口，不能宣称已经支持稳定续读。

验收必须经过“工具执行 → BiliClient → 假浏览器/HTTP → 结果校验 → 观察记录”，包含中文关键词、无结果、排序、第二页、URL 参数规范化、错误视频/搜索身份和暂停通道，不只测试 DOM 适配器返回对象。

## 7. D包：批量取帧与一次视觉分析

涉及 B站媒体提供者、浏览器桥接、媒体读入契约与媒体曝光记录。

### 7.1 能力可达

把 `bili_frames` 纳入统一能力声明，并由安装配置生成任务授权。使用同一声明生成注册信息和阶段工具清单。新增“已注册动作在对应任务政策中可调用”的装配检查，防止工具存在但模型不能使用。

### 7.2 浏览器采样

- 首版默认 3 帧，单批最多 6 帧；明确时间点优先。
- 一次必要导航后连续采样。`null` 表示正在等待/定位，继续有界轮询；真实错误单独返回。
- 批次有总截止时间，各点有有限等待时间，并为末尾校验预留时间，避免第一点耗尽预算后整批成功结果也被丢弃。
- 每帧核对视频与分 P，保留请求时间和实际时间。页面改变、取消、超时分别处理；未执行的点也必须有结果。
- 只有确认仍是同一浏览器会话、账号和视频时才复用页面。刷新、切页、账号变化使复用状态失效。

### 7.3 媒体输入与来源

新增 `mode=images, sources=[...]`，内部逐项取得媒体并建立租约；已取得资产可走兼容的 assets 分支。逐帧验证任务范围、可用版本和来源。

组内关系校验依据同一个视频/CID/批次及可信父来源。不同帧的 sourceKey、文件名、时间点和内容哈希本来就不同，不能要求完整 description 相等。

视觉服务一次接收整批图片。结果必须完整且唯一地映射到帧索引，拒绝重复或越界索引。曝光记录保存每帧来源和时间点；不能把第一张图的来源当成整个批次的来源。缺失音轨、采样范围和不确定性继续保留。

### 7.4 缓存与失败

请求幂等与内容缓存分开：重复 requestId 返回同一执行回执；内容缓存按视频身份、位置、内容版本和读取实现版本复用。视觉分析缓存还包含实际图片哈希、模型与分析规则版本。

相同图像出现在不同时间点时，可复用图像理解结果，但必须保留各自采样事实。部分失败只补缺失部分；失败或空字幕不得作为长期“无内容”缓存。

验收：正常 seek 先返回 null 后成功；3 帧只发生一次必要导航和一次视觉请求；第二帧失败时第一帧仍可使用；正确的两张不同帧可合并分析；错误账号、视频或任务来源不能混入；取消释放全部租约。使用真实 BiliClient、BiliStore、媒体服务和假视觉后端验证。

## 8. E包：显式阶段与工具范围

涉及 `harness-runtime.ts`、`native-runtime.ts`、协调器、通用工具派发与能力查询。

删除依据可用动作是否含 `bili_` 的阶段推断。拥有B站能力不等于当前任务正在阅读B站。

阅读阶段工具集合为“当前任务授权 ∩ 阅读阶段所需能力”，包括搜索、信息、评论、字幕、批量帧、媒体分析、阅读记录、来源续读和必要任务控制。一般任务维持自身工具能力。

工具可见性、原生工具注册、别名展开、`dsh_tool_call` 实际派发共同使用这份集合。不能仅隐藏名称，也不能让通用派发绕过阶段范围。

能力目录默认只列名称和短用途，详情按名称获取；阅读阶段不返回完整宿主目录。阶段提示词必须进入允许装配的 section 清单，避免注册后被过滤掉；同时处理通用“开发工具”指引与阅读阶段指引的冲突。

阶段在安全步骤边界切换。同一段内尽量保持工具集合稳定，切换不得扩大原任务授权。

验收同时覆盖阅读任务与普通工具任务；模拟任务授权清单同时含 B站与宿主工具时，普通任务仍能调用宿主工具；阅读阶段的直接调用和通用派发均受范围约束。

## 9. F包：执行中的上下文预算和持久接续

涉及任务运行循环、RuntimeStore、检查点、来源核验、WorkingViewPlan、压缩器、调度和最终交付。

### 9.1 工作视图

| 材料 | 当前请求中的形态 |
|---|---|
| 目标、约束、人格、任务来源、剩余预算 | 当前有效版本 |
| 当前视频和必要未处理材料 | 有限正文与短来源引用 |
| 已完成视频 | 有限数量的短结论与阅读记录引用 |
| 历史字幕、评论、图片分析 | 本地保存，按需分页 |
| 工具目录与能力状态 | 当前阶段当前版本 |
| 已完成操作 | 简短状态，详细回执留在账本 |
| 未知效果与未完成事项 | 必须携带的状态和核验入口 |

已看 ID、来源依赖和回执索引也要分页，不能把不断增长的列表换成 JSON 后继续常驻。完整来源依赖留在程序记录中，模型携带短引用；来源撤回时使相关结论失效。

工具结果的保留策略由程序声明：来源支持的阅读材料可以退为引用，能力目录等操作信息保留版本，未知效果保留核验状态。退役必须保持工具调用/结果配对，不能让模型把缺失回执理解为尚未执行。

### 9.2 预算与触发

初始值为试运行配置，按同条件回放校准：

- 单次输入软阈值 24k、硬上限 32k 估算 token，包含实际使用的工具定义，并为输出预留空间；模型窗口更小时自动下调。
- 每个阅读单元保存检查点；最多约 3 个已完成单元形成一段。
- 即使只读一个长视频，达到输入软阈值也要接续，不依赖先读满 3 个视频。
- 单元提交按唯一 ID/版本计数，不把重复保存当作新单元。
- 实际输入用量、估算输入、本地审计字节和累计任务消耗分开记录。核对适配器实际编码，不把 tools/toolHistory 两份内部结构直接当成两份已发送内容。

在下一次模型调用之前检查预算，而非等 `runExecution` 完成。所有当前工具已经结算、结果消息已配对后，可以通过受控的 `segment-yield` 返回协调器；不用任务失败异常冒充正常切段。

达到硬上限时不发送超预算请求。先有界整理或接续一次；若最小必要材料本身超限，记录具体原因并等待处理，禁止连续创建没有收益的新段。

### 9.3 接续事务

根任务记录 `rootRunId`、段号、原始截止时间及总预算。子段沿用这些限制，不能每段重新获得完整任务时限，也不能把同任务的无关重试总数当作段号。

检查点包含：任务/版本、阶段、阅读记录版本、当前游标、必要未完成事项、未知效果、来源引用、工具版本和剩余预算。完整历史留在原归档，不作为下一段输入。

交接流程：

1. 结算当前工具并保存可核验检查点；写入失败则不退出当前段。
2. 预检任务仍有效，原始来源与权限仍有效。
3. 同一个 RuntimeStore 事务将父 run 标为 `continued`，并写入具有稳定幂等键的子段请求/接续记录。
4. 事务提交后派发子段。派发前再次核验任务版本，重启恢复时扫描尚未派发的持久请求。
5. 新段使用明确不同的 sessionId；session key 纳入根运行、段号或检查点身份，避免重新选中旧会话。
6. 原 `messageSource`、发起者、政策、目标会话与来源资格由程序验证后继承，不能由模型重建。

重复恢复只能创建同一个子段。已经完成的操作从回执与内容缓存继续，未知效果进入核验，不能因换了会话自动重放。跨 B站库与运行库的记录通过版本引用和幂等写入协调，不能把两个独立 SQLite 事务描述为一个原子事务。

只有最终叶段的真正结果进入最终交付，整个任务沿用既有交付去重机制。父段内部结束不会发送中间总结。达到总预算或段数上限时，保留进度并明确未完成部分，不能把“禁止继续”解释为“任务完成”。

### 9.4 验收

使用真实协调器、运行存储、来源核验和接续逻辑，平台与模型采用可控假件。至少验证：

- 单个长视频达到预算时换段；20 个阅读单元后输入大小围绕目标范围波动，不随单元数量持续线性增长。
- 每段使用新的 sessionId，taskId 与交付目标保持一致。
- 检查点落盘前、父段交接提交后、子段派发前分别模拟进程中断；恢复后只有一个子段，无操作重复执行。
- 任务取消、目标版本改变、来源撤回后，旧检查点不得继续执行。
- 父段不产生最终交付，最终叶段只交付一次。
- 段号、时限与累计预算从根任务继承；达到上限时有明确的未完成状态。

## 10. G包：可核验的打包、部署和回退

涉及发布构建、安装准备、profile 更新与启动诊断。

1. 发布包记录源码提交、包版本、协议版本和存储版本，使用新的不可变目录；源码构建、包导入和配置检查分别验证。
2. profile 使用结构化 JSON 修改，仅更新预期键，以 UTF-8 无 BOM 写入临时文件；重新解析成功后原子替换。禁止用文本替换拼接依赖行。
3. 通过统一安装入口同步 package.json、依赖锁和实际插件链接。完成后核对真正解析到的插件路径及构建标识，不能只检查配置里写了什么。
4. 停止旧实例并确认占用释放，执行存储预检、备份与显式升级，再启动候选版本。升级期间禁止两个版本同时打开相同状态库。
5. 启动状态显示实际构建与数据版本。错误区分配置解析、插件导入、存储升级和平台诊断；现有B站暂停状态不会因部署自动清除。

回退分阶段处理：

- 数据尚未迁移：可以恢复旧安装清单、锁和链接。
- 已迁移但未接收新工作：停止候选实例，按升级清单恢复一致性备份后再启旧版本。
- 已产生新任务或新数据：不得直接以旧备份覆盖。优先前向修复，或经过验证的数据保留/降级方案；旧二进制是否识别新状态语义也必须检查。

候选包先在复制的状态库验证升级和重启，再进行受控的新任务验收。新版本不能借“桌面能打开”或 `check` 通过宣称功能完整。

## 11. 开发顺序与交付门槛

| 批次 | 开发内容 | 本批必须通过 |
|---|---|---|
| 1 | A包：恢复互斥任务收尾，建立真实协调器测试入口 | 完成、等待、取消、异常无挂起；原有任务交付不回归 |
| 2 | 统一契约；B包：任务隔离、记录版本与显式迁移 | v2/v3 升级、错误身份零写入、跨任务隔离、保存幂等 |
| 3 | E包与C包：显式阶段、授权装配、搜索与评论续读 | 一般任务不失去工具；有效搜索不被错拒；游标可继续使用 |
| 4 | D包：批量帧与多图分析 | 冷启动 seek 成功、逐点状态完整、一次视觉、来源逐帧有效 |
| 5 | F包：执行中预算、检查点和原子交接 | 长任务不线性累积、重启恢复幂等、仅最终交付 |
| 6 | G包：发布与状态升级演练 | 三处安装记录一致、真实加载版本正确、可核验升级与回退 |

每批只增加能证明行为的测试：重点是原缺陷的反例和跨模块调用链，不用重复的参数测试替代装配验证。相关检查通过后再推进下一批；不以扩大测试数量作为完成度。

最终报告同时交付：

- 对照固定素材的模型步骤数、平台请求数、导航次数、视觉请求数、缓存命中、输入大小和分阶段耗时。
- 每个阅读单元的真实覆盖范围与缺口。
- 任务状态/交付、数据库升级、普通工具任务的回归结果。
- 新发布包与源码的对应关系、实际加载版本和备份清单。

发布完成的判据是：上述阻塞问题全部关闭，完整调用链和接续恢复验收通过，正式实例加载的版本可确认。任何未完成项都应明确保留为缺口，不再把“有类型定义、有工具入口、局部测试通过”记作功能完成。
