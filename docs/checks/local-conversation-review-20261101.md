# 0.26.2 本机实际对话复盘与下一轮方案讨论

2026-11-01，检查范围：北京时间 15:12—15:55 的本机 QQ 对话、对应 DSH 会话、运行账本、上下文审计和工具回执。运行程序仍为 0.26.2 / `4ecbe09`，工作区基线为 `6e1f7e0`。本轮没有修改程序、配置或部署，没有访问服务器，也没有触发模型或平台请求。

## 结论

用户要求“自己挑一条视频，看过内容和评论再汇报”是合理、具体的任务。四次尝试均实际启动，但全部在本地阅读容量检查处失败；25 次 B站工具操作全部返回 succeeded，没有通用 DSH 工具或媒体理解调用。不能把失败归因于用户给的范围太宽，不能把工具返回成功等同于看懂视频。

上一轮解决了 QQ 分条、目录超大和部分接续入口，但验收不足以证明真实任务能够完成。脚本模型的 20 视频测试没有覆盖生产提示、完整工具装配、自然语言确认和真实模型选用工具；HTTP 与工具目录的单独成功也不能替代端到端验收。

## 1. 预算检查把新会话也堵住了

指定 BV 号任务的首次请求审计：

| 项目 | 现场值 |
|---|---:|
| 本地估计输入 | 28,900 token |
| 阅读固定硬阈值 | 32,000 token |
| 工具定义 | 25,413 字节，19 个工具 |
| toolHistory | 25,436 字节 |
| 当前任务输入 | 6,444 字节 |
| 运行上下文（含本地来源元数据） | 23,594 字节 |
| 其中能力索引文字 | 9,978 字节 |
| 已读工具结果 | 0 字节 |
| SDK 报告的模型窗口 | 1,000,000 token |

这里的 28,900 是程序估算，不是模型返回的实际输入用量。第一次成功请求的平台回执报告总用量为 14,856 token（包含输出）。两个指标不能直接等同，但差异与实现相符：预算按完整审计对象计算，将 `source.sections` 等本地元数据算入；同时统计 tools 与 toolHistory。SDK 后续还会做工具历史投影，真实请求不等于这份审计对象。

0.26.2 的软阈值公式在该输入下得到 31,999，比硬阈值仅少 1。实际都是 hard-token-budget 才切段，未给整理和检查点留下独立余量。新段继续带全部固定工具、能力索引、前段操作列表和新增“待反思经历”，固定成本反而上升；只要首轮估计加 1,000 达到 32,000，就不再允许调用模型。换会话因而不能解围。

代码位置：`packages/core/src/context-plan.ts:55`、`:89`；`packages/core/src/native-runtime.ts:34`、`:40`、`:41`。

建议：将内存/审计字节上限、适配器实际请求估算、模型窗口和工作段预算分开。复用 SDK 的真实投影口径，校准平台用量；不能简单删掉所有 toolHistory，因为历史工具变化仍有语义。先减少固定装配，再制定有明确收尾余量的软阈值。新段首轮不能取得足够工作余量时，应在程序层缩减装配或报告配置问题，不能要求用户不断缩小正常任务。

## 2. 任务没有承接对话中已经确定的意思

15:39 的模型并非没理解“可以”。其 `qq_task_submit` 参数标题已经明确写出：在 B站挑一条时间靠前、有热度的养鱼视频、认真看完、读一页评论、只走养鱼、候选少量。

但 Core 对显式任务直接使用当前消息的 `directive.text` 作为 title 和 goal，忽略提交标题，也没有把原任务、前面的方案和本次确认绑定成完整目标。所以任务执行器收到的真实目标只有“可以”。15:16 的纠正同样成为独立新任务，原来的题材和交付要求没有作为任务目标延续。

代码位置：`packages/core/src/execution-coordinator.ts:137`、`:141`；`packages/contracts/src/message-task.ts`；`packages/channel-qq/src/tasks.ts:12`、`:35`。

建议：增加带来源的任务意图承接，区分新任务、补充、纠正、同意、重试、继续和取消。保留原目标、最新有效限制、用户授权的决策范围、交付要求及关联消息。模型可以解释并整理目标，程序验证来源、当前会话、主人身份、版本和撤回状态；不能用模型改写来扩张权限。明确的“可以”应绑定刚才的方案，不生成“可以”任务；只有无法唯一关联时才询问。

## 3. 接续保存了部分入口，没保存完整工作状态

搜索阶段的工作视图始终是空的：total=0、resume=[]。`readingResume` 只从 video 页面起步，不包含搜索词、已返回候选、选中理由和待比较项。第一轮只有搜索结果，接续又只带操作名称而不带候选状态，于是重复搜索。

指定 BV 号时已有视频、字幕和评论入口，但六个已捕获画面的 source 引用没有进入 resume，也没有明确“图片已获取、尚待视觉理解”的下一步。待反思经历则随接续新增，并占用同一个紧张的工作区。

代码位置：`packages/bilibili/src/reading-resume.ts:15`、`:24`；`packages/core/src/execution-coordinator.ts:754`。

建议：保存覆盖全过程的有界工作状态：原目标 → 搜索与候选 → 已选视频及理由 → 已读字幕区间 → 已采样/已理解画面 → 评论游标 → 已形成判断与未完成项。正文留在来源库，工作区只保留简要事实和可验证入口。每次工具操作后由程序更新状态，模型补充判断；不能等模型主动写总结才算有进度。新段优先恢复未完成步骤，完成的动作不从头重跑。非当前任务所必需的反思提醒延后或单独分配预算，不删记忆、不解除来源校验。

## 4. 工具“可发现”和“会完成任务”仍有断层

阅读阶段实际提供 19 个工具，每次都带完整参数。与此同时，它明确禁止读取宿主工具目录，并跳过 DSH 目录刷新。模型看到的 host 状态为：configured=true、available=false、code=null、execution=authorized-task、tools=[]、skills=[]。

这是程序主动施加的阶段限制，不是本轮发现了 DSH 掉线。目录分页虽已实现，阅读执行器仍无法发现并选择适合当前问题的宿主能力。能力提示也没有明确区分“安装了”“本阶段隐藏”“本任务可执行”和“依赖不可用”。本轮找到的 QQ 测试记录中，没有直接要求查询 DSH 工具的独立对话，也没有 `dsh_tool_list`/`dsh_tool_call` 调用；若用户指的是另一段对话，应以那段记录另行核对。

代码位置：`packages/core/src/harness-runtime.ts:16`、`:17`、`:83`、`:110`；`packages/core/src/execution-coordinator.ts:833`。

建议：保留常驻的小型只读能力索引，明确阶段限制及原因；执行工具按当前步骤按需装配。搜索、字幕、评论、画面理解不必同时携带全部通用工具。普通故障可在原任务权限内选择已支持替代路径；确需宿主能力时由程序核对任务权限后切换所需工具组，不给全部工具开口，也不让一次浏览失败自动升级成改代码、改配置。现有执行器即可完成，暂不引入子代理。

稳定的衔接应由程序承担，例如视频定位后解析分 P、字幕轨与游标，截图后把 source 交给视觉读取。Agent 负责选视频、选择阅读重点、评价证据和决定是否深入，不必反复手工拼接每一个 ID。

## 5. 失败说明把内部限制转交给了用户

四次失败通知多次要求用户选题材、限定范围，最后指定一个视频后仍要求在字幕、评论和画面中挑一块。这与“如何选择由你自己决定”冲突。

通知生成器主要拿到动作名、succeeded、操作数量和错误码，没有完整原目标、用户已委托的选择权、具体覆盖状态与可恢复步骤。它据此补写了“范围太宽”和“缩小就能继续”的解释，后者未经验证。15:55 的“字幕、评论和画面都读了一遍”也不准确：字幕只是轨道列表，图片只是捕获，尚无媒体理解操作。

代码位置：`packages/core/src/native-task-delivery.ts:75`、`:78`。

建议：事实字段分清“已获取资源、已读取正文、已理解、已整理、已交付”。反馈始终带入原目标和最新约束；只陈述可验证进度。内部容量/配置问题归为内部阻碍；能自动恢复的继续处理，不能恢复时明确说明具体阻碍。只有权限、登录或用户偏好确实缺失，才请求用户补充。不能未经排队就承诺继续，也不能把内部接续计数当成用户已完成任务数。

## 建议开发顺序

1. **先修任务承接和预算口径。** 用“原任务 → 自主选择要求 → 可以”与指定 BV 两条现场链路建立失败复现；核对真实生产工具装配的固定成本。目标不是先提高总容量，而是让合理短任务有足够处理和收尾空间。
2. **补全工作状态和读取衔接。** 支持搜索候选和未理解画面恢复；为单个视频贯通字幕正文、画面理解、评论与最终表达，保留覆盖范围。
3. **重做能力呈现和按需装配。** 能力可发现与执行授权分开，提供明确的阶段切换路径，避免目录可读但工作阶段仍无路可用。
4. **修正进度与失败反馈。** 不再把程序限制解释为用户要求过宽；自主决策在授权范围内真正执行。
5. **最后做真实完整验收。** 回归是基础条件，另验证真实模型在生产配置下从用户原话到结果的全过程；成功后再讨论活跃度。自主触发不应让失败任务更频繁地重复。

## 本轮应采用的验收标准

- 原样回放本次用户措辞，检查任务保存的完整意图和关联消息；“可以”不得成为裸目标，纠正不得丢掉原要求。
- 真实装配下测量首请求、工具结果后、接续首请求和收尾请求；所有阶段都留有实测工作余量，不通过关闭来源校验、清库或无限增大上下文过关。
- 强制在搜索后、采样后和字幕分页中途切段，下一段能继续相同任务，不重复搜索、丢帧或遗漏字幕下一页。
- 指定 `BV1JPx16tEWG`：取得正文，必要画面真正进入视觉理解，读取评论，并形成有证据的汇报；轨道列表不能充当字幕正文，抓图不能充当已看懂。
- 自选视频：在少量候选中自主决定，并说明选择与覆盖；不要求主人替它执行筛选。
- DSH：从普通聊天发现能力，再在相应任务中调用一个获授权的只读工具，使用返回结果完成回答；不是只证明目录能列出名称。
- 故障注入：平台受限、凭据过期、无字幕、画面过期、容量不足分别反馈，并验证可行替代路径；不能统一说“范围太宽”。
- QQ 最终交付继续核对真实回执；不把生成了正文或命令受理当成交付成功。
