## 查到的原因与修复

### QQ 消息条数

原实现已有可选的 `qq_messages` 契约，但普通正文会变成一个语义消息；换行不是消息列表。渠道账本保存了逐条回执，Core 却只取得部分进度，模型没有完整计数反馈。

现在明确要求 QQ 最终答复用消息列表，每项通常一到两句话；旧的普通正文采用按句分条。显式消息边界、代码和引用保留，超长文字仍按 800 字符传输限制分段。当前会话最多注入最近六次发送的计划、已确认、待发、发送中和未知条数，不重复注入整段正文。已保存发送计划保持原边界，未知状态不自动重发。

真实 Core、DSH SDK 循环和 QQ 发送账本连接到本机模拟 OneBot，验证三条消息对应三次发送及三个回执；下一次模型输入确实包含 confirmed=3。另验证跨会话隔离、有界计数、媒体顺序和旧计划恢复。没有给真实 QQ 联系人发送验收消息。

### B站任务失败与反复接续

服务器在北京时间 11 月 1 日 01:38 左右处理 `BV1JPx16tEWG` 时，已成功取得视频资料、字幕轨及部分字幕。其后不断从视频资料重新开始，最终报 `SEGMENT_LIMIT_REACHED`；聊天却把任务失败说成 B站没有打开。另一次任务是 `MODEL_INCOMPLETE`。两者不能证明网络连接失败，现场另有大量 HTTP 成功记录。

请求审计显示首轮固定输入已约 22,335 个估计 token，其中工具与工具历史各约 23.6 KB；24,000 的软阈值很快触发。后续新会话的固定输入逐渐升到约 25,938 个估计 token，几乎每次只做一步就再次接续。阅读工作视图只含模型主动保存的判断，未保存判断时没有视频页与字幕续读入口。

修复内容：

- 接续视图保留本任务实际已观察的视频页、分 P、字幕轨和 nextOffset；没有保存判断也能继续读取，不把空判断记录当作没有阅读。
- 新会话的软阈值考虑固定输入成本，尝试留出 4,000 token 的工作空间，同时仍受原 32,000 硬上限、模型窗口、字节上限、时间及接续次数限制。固定输入几乎挤满硬上限时明确停止，不制造空接续。
- 字幕轨列表不要求有效时间区间；正文默认区间受视频时长与六分钟上限约束。
- 浏览器未配置时不注册 `bili_frames`，安装器同步生成相匹配的权限动作；HTTP 媒体链路仍可使用。
- 阅读记录对外把分页标识叫作 `cursor`，避免内部 `token` 字段触发凭据过滤而使整份回执消失。内部数据保持原格式。
- 失败反馈包含前序接续中的实际操作及动作名称，明确区分模型/容量失败与平台连接失败。

20 个视频的离线集成验证完成 41 次模型调用、20 次模拟平台读取、7 个会话；每次请求在原硬上限内。新增回归验证尚未保存判断的续读入口、任务隔离和来源失效，以及高固定输入下能继续多步工作。

### DSH 能力目录

服务器北京时间 01:34、01:56 的两次 `dsh_tool_list` 实际返回 `ACTION_RESULT_TOO_LARGE`、data=null。完整目录一次返回超过 Core 的 128 KB 结果上限，模型把正文丢失误判为空表；能力提示在过大时也会清空列表。

现在目录默认只分页返回名称与简短用途，支持关键词筛选、按名称读取参数/技能说明、按 next 续读和目录版本核对。详情在分页前完整脱敏。提示过长时保留总数与样本，并说明截断不等于没有工具。没有放宽通用工具执行权限，也没有把通用执行工具加入 B站阅读阶段。

180 项大目录离线验证无遗漏、无重复，单项详情能跨页重建。真实本机 DSH 桥接验证取得 54 个工具、14 个技能，工具目录共 5 页，最大 4,362 字节；实际读取 `read` 的参数详情。验收没有执行目录中的工具或调用模型。

## 用户检查建议

1. 在本地 QQ 要求“请分三条消息说明你能做什么，每条一到两句”，随后问“刚才实际发出了几条”；对照实际气泡和回答。
2. 请本地大肥鱼阅读上述 BV 号的视频和评论。区分实际取得的文字、画面、音轨；局部缺口应明确，不应因任务未收尾就宣称整个 B站离线。
3. 询问当前 DSH 工具，并指定一个工具查询参数；应能分页发现能力，不把截断/错误说成空目录。

检查通过后再由用户上传 GitHub、在服务器重新部署。本轮没有替用户执行这两步。

## 活跃度留待讨论

本地配置目前关闭了自主活动。服务器记录中存在后台自主任务，因此“少主动说话”不等同于“没有任务触发”。后续宜先明确想要的是主动问候、分享发现还是阶段反馈；提示词决定何时值得开口、如何表达，触发器决定时机、频率及冷却。先讨论边界，再开发，不直接加密循环唤醒。
