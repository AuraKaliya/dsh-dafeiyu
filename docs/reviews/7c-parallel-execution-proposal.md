## 二、现在可以并行的工作

1. **主协调者**独占真实执行、恢复、上界计费、阶段调配及证据导出。所有付费请求仍经现有账本。
2. **预算／时间监督子智能体**读一致的只读快照或协调者发布的快照，检查60元、6小时、原到期、未知费用及在途数；只报告，不取得租约、不恢复账本、不发模型请求。高频重复扫描没有必要。
3. **证据监督子智能体**核对已关闭attempt的不可变文件、hash、调用起止和基线来源。只能审查已完成的证据；不复制活跃SQLite数据库，不读取仍在变化的会话当作最终证据，也不自行调用会写入并取得租约的导出入口。
4. **场景／源码审查子智能体**并行检查失败分类、H组配对、遗漏和恢复计划。AI语义预审只作辅助意见，不填写人类已通过，不替换原始程序结果。

当前真实验收期间，不在同一checkout运行 `npm test`、构建、安装依赖或修改任何被指纹覆盖的文件：受管测试入口首先构建，会写 `packages/*/lib`。以后可以在独立D盘开发副本做相关离线测试，使用它自己的依赖、输出和 `.runtime/tests/`，绝不在那里建立第二份真实campaign。实际测试仍统一从 `npm test -- 指定文件` 进入；单次入口内已有最多4路并行，多个子智能体各自抢同一个测试入口没有收益。重CPU／磁盘工作还应避开正在接近请求截止时间的真实批次。

### 受管测试的实际并行能力与冲突边界

`scripts/run-tests.mjs`先取得 `.runtime/tests/.runner.lock`，再按顺序执行一次产品构建、一次测试编译、一次tooling类型检查；之后才进入 `scripts/testing/driver.ts`。后者采用 `isolation: 'process'`，文件并发为 `max(1, min(4, availableParallelism() - 1))`。因此应由一个执行者把相关测试文件的并集合并到一次受管入口，利用已有的文件进程并行。活跃锁会使另一入口报 `TEST_RUN_ALREADY_ACTIVE`；这个锁也不代表真实验收被锁住，受管测试与真实执行器有不同的锁，必须由主协调者禁止共享checkout交叉运行。

共享编译写入包括 `packages/*/lib`、composite项目的 `.tsbuildinfo` 和 `build-tests/`；`scripts/testing/tsconfig.json`只是noEmit类型检查。不能让子智能体绕过入口分别运行编译、直接执行driver、删锁、修改环境骗过受管检查，或并行改写这些产物。单次构建结束后，运行中的各测试进程仅消费冻结的编译结果，监督代理只读它们。

preload会给每个测试进程分配独立的 `run-<id>/workers/worker-<id>/tmp` 与 `dsh-home`，并设置相应TEMP／TMP／DSH_HOME；**同一run的HOME／USERPROFILE目前共用 `environment/home`**。因此进程隔离不等于所有路径隔离：涉及固定home路径、固定端口、环境外文件、共享外部服务或原型级全局夹具的测试，须先证明没有跨进程资源竞争。新并发专项夹具优先全部放在worker独有临时目录，使用独立数据库、动态端口和虚构后端；不能接触正式campaign。发现共享home副作用时，先移出并行集合并交主协调者决定独立受管安排，不临时绕开入口。

## 三、最小安全架构

采用同一个Node进程中的两个异步场景worker，复用同一个 `EvaluationWorkspace`／`EvaluationLedger` 实例。worker不是独立CLI，也没有自己的总预算或clock nonce。保留现有工作区租约，协调者只调用一次 `startExecution`，全部worker关闭、证据封存后才 `stopExecution`、释放租约。

冻结独立的调度策略记录：版本、最大场景数2、付费全局并发2、每attempt最多一笔在途、启动顺序、互斥键、排队规则、停止和计时口径。将策略hash放入控制器证据与执行开始审计；默认／旧路径仍为1，不能通过任意环境变量绕开上限。总预算、价格、首次调用、累计已用时间和原授权文件不重写。首次实现只并行同一批formal场景；校准与单项恢复仍通过一个阶段执行区间，不混用账本的phase。

每个场景继续使用独立的 `cases/<attemptId>/profile`、Context、会话和夹具状态。DSH_HOME／TEMP在协调者启动前设置一次，不在worker中改进程级环境。供应商匿名标识等共享初始化要串行完成或证明只读安全；禁止共享可变产品会话。所有工具动作仍限本机虚构环境。

### 固定启动顺序与H组互斥

- 启动队列严格来自原manifest，保留批次边界、skip-pass和retain-failure规则，不按预期速度或分数挑选。完成顺序可以不同，报告仍按manifest显示，并另存实际开始／结束时间。
- “开始”必须是协调者持久登记的 `attempt.started` 顺序，不能用创建Promise的先后冒充。为避免后项先派发，首笔请求还须按同一序号完成准入；若前项准备期尚未到达首次派发点，后项等待该启动屏障。前项在首次派发前失败，则关闭新准入。
- 对连续性场景使用 `(candidateHash, calibrationNamespace, sampleId, repeat)` 互斥键。H01重复1的full、compressed和compressed-restarted共用一把锁；不同重复的独立基线可以分开。锁从基线接纳前保持到场景运行、关闭及证据封存完成，不只包住文件写入。
- 若队首被同组锁占用，等待；不跳过它启动更后面的容易样本。允许因此暂时只有一路，不能用吞吐理由修改冻结顺序。
- 基线准备只有一个创建者，其他分支使用同一已关闭快照；继续校验sampleHash、candidateHash、logicalHash、来源与输入曝光。复制仍用SQLite备份和独立普通文件，禁止硬链接和活动库复制。
- `admitCompatibleBaseline` 的目标文件和接纳证明必须成套发布、可恢复。不得把“目标存在、证明尚未落盘”默认为合法复用；应辨别自然准备与跨候选接纳的来源，缺必要证明时阻断。
- 共享目录创建和同名证据发布通过协调者串行处理，或在EEXIST后重新核验目录类型与链接安全；保留 `wx` 和hash。不能忽略 `workspace.write` 的竞争，靠随机attempt路径只能避免部分冲突。

调度器必须观察每个任务的真实启动与结算事件，而不是对整个数组直接 `Promise.all`。一项失败后先关闭准入，再以 `Promise.allSettled` 等待所有已启动worker收尾；不能因首个Promise拒绝就关闭账本、导出或释放租约。

## 四、费用准入必须分清等待与耗尽

新增共享异步准入器，例如 `EvaluationAdmissionBroker`，接在 `installEvaluationBilling` 之前的派发点。模型输入、工具、effort和输出边界保持冻结；等待不能修改这些内容。任务、历史准备、摘要、修订及辅助调用统一经过它，不能每个worker各建一个“并发2”队列。

账本仍是最终权威，每次实际准入在一个 `BEGIN IMMEDIATE` 中重新检查：nonce所有权、阶段、授权截止、累计时间、全局停止状态、未知费用、总／阶段资金、总在途数小于2、该attempt无在途及请求键未使用，然后原子插入预留和审计。异步等待不能持有SQLite事务。只在确实准入后记录调用开始；队列中取消不产生虚假的付费派发。

设总限额为B，已结算与上界计入为S，当前reserved合计为P，待准入上界为Q；未处理未知费用单独触发停止，不参与“以后可释放”的计算。

| 条件 | 准入结果 |
|---|---|
| 有未处理未知费用、证据故障或到达硬时限 | 停止新准入，进入收尾 |
| 在途数已满，或同attempt仍有在途 | 排队，等待结算或取消 |
| `Q <= B - S - P`，且阶段份额也够 | 原子预留并派发 |
| 当前不够，但P大于0，且 `Q <= B - S`；阶段同理 | 暂时等待，不能报预算耗尽 |
| 即使现有预留全部释放仍不够，或结算后无可释放预留且仍不够 | 确认对应总／阶段额度不足，停止新增并收尾 |

例：可用2.5元，A预留2.131072元后，B只能排队。若A实际结算0.02元，B可准入；若A结算导致仍不足，才记录真正预算停止。阶段额度也要作同样判断，不能只看总余额。仍使用完整模型上下文的安全上界，不用字符估算降低预留；也不为了保留两路而拒绝本可单路继续的请求。

队列按稳定的请求登记顺序公平唤醒，避免摘要被普通请求挤压。每次唤醒重查全部门槛；等待有AbortSignal和绝对截止时间，取消必须移除队列条目，不遗留许可。等待期间不计入供应商请求时长，但计入场景／Run及本轮机器时间；120秒请求计时从实际派发开始，不能重置240秒Run和5／15分钟场景限制。若首次准入尚不可行，尽量在创建attempt前排队，避免仅因没有槽位制造新的场景失败。

未知费用或证据错误产生时，关闭新场景与新请求准入，并拒绝所有尚未派发的等待者。**已经发出的另一路请求继续在原截止时间内读取用量并结算；不要只因同伴未知就主动取消它，制造第二笔未知费用。** 已获得预留但不能证明未派发的请求仍保守处理，不自动退回费用。总时间／48小时到期、隐私或权限事故是例外：立即取消相关在途，并保留未知费用及现场。

结算、调用结束证据写入和队列唤醒的顺序要固定；写证据失败也停止新准入。即使协调者已经停止，合法在途请求仍允许结算和记录finished。所有worker和请求收尾后，才允许按现有授权作上界计费；保留原实际费用未知标签，禁止在仍有reserved或running attempt时解除停止。

## 五、计时、证据和恢复

**沿用现有单机器执行区间的累计墙钟时间。** 两路重叠的10分钟计入本轮机器10分钟，不变成各自拥有6小时，也不重置已用时间。另报两个worker各自耗时及其合计，用于性能分析，不把它冒称原授权时钟。协调者等待、准备、请求、工具、摘要、重开、关闭和证据导出均在活动区间内；只有全部排空后的人类等待可以暂停，48小时仍连续流逝。

所有派发使用剩余机器时间、原48小时截止、场景截止和请求上限的最小值。全局停止需要能唤醒排队者并取消到限在途，不能等一个无许可的worker永久卡在 `whenIdle()`。崩溃恢复沿用保守收费：单clock的未观察间隔照计；不按“可能已经结束”返还时间。

证据增加调度策略hash、批次ID、worker编号、manifest序号、attempt ID、首次准入序号、H组键、排队原因／时长、请求reservation ID、实际并发峰值、停止原因及停止时的在途集合。原requestHash、sessionHash、usage分类和profile证据继续保留；不落凭据、内部思考或私有replay状态。完成worker可立即封存自己的关闭profile；整批导出仍等待所有worker关闭，由唯一协调者完成。资源检查也集中处理，不让两个worker反复遍历正在变化的整个证据树；磁盘20 GiB余量、证据10 GiB上限继续适用，并考虑两路在途增量。

恢复按下列顺序执行：

1. 获取原工作区唯一租约，确认原所有者已退出；活跃、无权探测或PID复用疑虑均不能抢占。
2. 对原账本做显式恢复：所有遗留running attempt追加interrupted，所有reserved保留为unknown；原成功结果不改写，原首次调用和累计时间不清零。
3. 检查已发布基线与接纳证明，保留未完成准备的证据；没有完成标记的半成品不能作为已成功基线。不得为提速删除失败资料。
4. 等无活动请求、无running attempt，逐笔按现有授权处理可证明上界的未知费用；超上界或来源不清者继续阻断。
5. 从最早未完成项恢复，按现有明确复测规则追加attempt。并行中后项已经成功时保留它，恢复前项后可skip-pass，不能重跑后项收费；前项失败仍需原规则审查，不能因后项完成就跳过。

## 七、本轮不建议切换真实并发的原因

修改ledger／billing／runtime会改变已冻结的runtimeHash；现有H01／H05单文件证书会正确拒绝复用。最低成本路径也需要新候选校准；旧矩阵结果与基线能否继续归入该候选，还要另行证明调度变更未改变输入、权限、超时和证据语义。不能扩张现有证书白名单，或把并发控制代码从指纹中拿掉来省校准。

若以后专门建立“只改调度”的兼容证明，它必须列出全部变化文件、证明模型输入／评分／产品字节不变、覆盖排队和收尾的新边界，并保留旧结果所依据的候选及实际并发条件；仍需检查真实并发的网络表现。当前实现不具备这一证明，不能先并行再补写兼容结论。

因此本轮优先把剩余金额用于原顺序中可完成的真实样本，把多个子智能体用于监督和审阅。只有在停止点重新核对后，明确证明两路改造与必要校准不会挤占剩余必需验证，并且时间已成为主要瓶颈，才值得切换；当前快照不满足这一条件。预算或时间耗尽时如实保留未完成项，任何并行方案都不能保证原60元内完成全部162项。
