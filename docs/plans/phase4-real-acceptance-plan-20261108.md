### 3.2 预算控制与停止

1. 验收侧以“已确认费用 + 未知费用的保守预留 + 在途请求预留”检查**批次和总额**。发起下一物理请求前预留其可核对的输入/输出上界及可能费用；不能只每分钟看一次余额。
2. 70% 发出费用预警并记录剩余必需场景；90% 不再发起新任务/新样本，只允许已经预留足够额度的请求收敛。需要下一个请求才能继续的工作先暂停本次验收；保留原任务，不悄悄动用别批额度。
3. 下一请求无法在剩余额度内预留，或费用上界无法确定时，不发送该请求。不得为了满足预算把固定业务目标自动裁剪；通过既有取消/暂停路径终止测试时记为未完成，并保留副作用未知与检查点。
4. 运行中取消不代表供应商停止收费；未确认结算的预留不释放。驱动若不能在发送前约束在途费用，必须在 P0 补齐或使用可核对的供应商额度保护，不能宣称已有严格金额上限。
5. 超出预计请求量 2 倍、相同无进展请求反复出现、未解释的付费请求、身份/费率失配立即停发新请求并诊断。次数是测试异常预警，不变成业务总步骤限制。
6. 每批只执行已冻结样本；既有传输重试全部入账，不在外层再套无限重试。401/402、权限或账户问题停止该批，不自动充值、换账号或换模型。

## 4. S1：核验语义复验

### 4.1 固定样本与收集方式

使用 `tests/fixtures/acceptance/verifier-cases.json` 的现有 24 例，语料摘要为 `fd61f9da9aeab4237a7525cab2822c698f6d2d87bf95f9d906de3d337dbd869a`。校准集 16 例为 9 个应拒绝、7 个应接受；保留集 8 例为 4/4。原准备包在 `.runtime/calibration/phase4-0.28.13/`，只读复用，真实观察写入新目录。

采集走候选的 `verifyPersonaDelivery` 路径和同一证据/候选正文，保留真实指令、正文、模型参数和 SDK 投影摘要。不能用一个看似相同的裸 API 问答替代程序核验。该入口当前选择可用的低推理档位、温度 0，按原逻辑使用 8,192 输出额度，必要时增至 16,384，并有既有只读传输重试；真实参数和每次尝试以采集结果为准，不为本次验证另行调整。答案表只交给审计端。

一个“语义判定”可能包含多次物理请求。收集原始尝试、结束原因及最终结果；供应商错误、格式错误、超限和取消均与事实拒绝分开。`replay-verifier.ts` 每份观察文件不允许同一 case/request 重复，所以主集合、固定复测和故障后补测分别保存，不能覆盖第一次失败来挑成功结果。

### 4.2 固定执行顺序

| 批次 | 样本 | 通过标准 |
| --- | --- | --- |
| S1a | 16 个 calibration 例，每例一次判定 | comparable=16、falseAccept=0、falseReject=0；unavailable/invalid/notExecuted 均为 0 |
| S1b | S1a 通过后才跑 8 个 holdout 例，不事先据其响应调参 | comparable=8，其他条件同上；保留集单独报告 |
| S1c | 以下 8 个预定高风险例，在新的独立会话再各测一次 | 8/8 与预期一致；和第一次结果一起保存，不当作额外 8 个独立题材 |

固定复测例：`cache-does-not-prove-absence`、`cache-scope-limited`、`uncertainty-not-immunity`、`partial-delivery-scoped`、`holdout-unknown-effect`、`holdout-unknown-effect-scoped`、`holdout-inference-promotion`、`holdout-inference-attributed`。

**任何误放或误拒都不进入下一门槛。** 不用平均分掩盖“未知当成功”“推断升格事实”或正确限定被拒。HTTP 失败、非法 JSON、缺少段落等不算正确拒绝，也不算可比较语义样本；结束时仍缺一个样本即未通过。

S1a 有缺陷先回到局部定位，确认修复后按实际改动决定需要重做的集合。若看过保留集结果再据此调提示词/行为，旧集合只能作为已见回归；需补新的盲保留样本、独立预标注和审计，再冻结后继候选，不能继续把旧题当未见集。

本门槛只证明这批固定样本的真实表现，不声称模型一般误判率为零。回放程序本身仍输出 `realModelCalled:false`、`semanticReliabilityProven:false`；真实采集凭据、输入一致性及人工复核另写 `semantic-audit`，不得改回放的语义来制造通过。

| S2-02 原任务修订 | 原任务执行中 → “只看已取得的片段，不要补下载” | 同 Task 新意图；最新禁止事项有效；旧运行不能覆盖新要求，待办如实保留 |
| S2-03 确认及歧义 | 仅一个待确认对象时“可以”；随后在多对象歧义下再确认 | 前者关联原目标，后者澄清；不无故新建无关任务或猜目标 |
| S2-04 只读状态询问 | 一个部分完成/待交付任务 → “现在做到哪了” | 分开说明目标、执行、交付；不重跑业务、不调用交付恢复；询问本身的对话模型请求正常记账 |
| S2-05 取消/撤销来源 | 任务进行中或首段已确认 → 已认证主人取消/获准测试来源撤回 | 控制受理后没有新的旧任务副作用；已发部分和未知结果如实保留；旧第二段、旧通知、旧恢复不能绕过 |
| S2-06 继续/重试及故障通知 | 已获成果，但生成或核验被确定性故障阻断 → “继续把结果发给我” | 路由到交付恢复；同 Task/Run/交付 ID；业务读取不重复。核验故障重用同候选和证据；系统故障通知的额外模型请求为 0，最终送达才认定交付完成 |

每卡固定一次完整顺序；真实模型可以使用不同但合法的工具路径，不要求文字逐字匹配脚本或走固定请求数。业务接续允许合法的新 Run，但须关联原 Task、前序进度和意图；纯交付接续不得换成果/目标或伪造新任务。

所有卡通过后才进入成本比较。错误控制、误完成或来源越权属于阻断问题；只对失败卡及受影响邻接分支复验，不因一句错误重新付费跑完整故事。

## 6. C1/C2：实际用量、账单和费用比较

### 6.1 从 P1 开始收集，不修改原账本

当前 Core 在 `model_requests` / `model_request_inputs` 记录本地请求与适配前输入；本地 ID 是程序生成的标识，**不能直接当作供应商计费请求 ID**。表中没有完整单价、金额和付费 Search/Fetch 明细；P0.2 必须补齐验收侧关联，不改写不可变历史。

每条物理调用至少有：验收运行/批次/场景 ID，本地请求 ID、供应商请求或账单关联 ID、尝试号，Task/Run/session/phase，模型与解析版本，发送与结束时间，四项 token 分量，供应商原始 usage 引用，价格版本/币种/费用，结果、未知原因和是否真正发给供应商。工具/媒体调用用独立记录关联父请求；不把同一外部计量标记再当一个新付费请求。

正式实例、确定性测试、真实局部复验和两小时观察分别汇总。协议虽有 `runtime` / `deterministic-test` / `real-validation` / `observation` 标签，普通启动并不会仅凭目录名自动取得后两种分类；驱动须验证完整传播。若采用包外清单关联，则以独立实例和明确请求集合映射分类，保留库内原标签，不能事后改库伪造。

按请求开始集合及结束快照对齐所有会话/任务/媒体/生成/核验/整理/恢复等阶段。Run 结束后发生的生成或核验请求仍归原成果；SDK 内层重试若对应多个供应商请求，应逐个关联。`sdk-pre-adapter` 字节只作重复输入分析，不换算成账单 token；总 token 已含缓存，不能再相加一次缓存量。

### 6.2 C1 账实一致的通过标准

- **100% 调用可归属**到本轮批次及实际阶段；100% 物理请求有已结算记录或明确待结算记录，不能把 `unassigned` 简单隐藏。采集器的独立校准请求可没有业务 Run，但必须有 case/batch 关联。
- 完成批次时无未解释额外调用、重复计费关联或未结束请求。已知 token 的分量之和精确等于总量；输入、缓存读/写和输出按实际适配器语义核对，推理 token 不重复计算。
- 供应商账单金额与逐项计价可核对；金额差异不超过官方可说明的舍入误差，缺少舍入说明时最多 0.01 元/批，超出即查明原因。跨费率时段按供应商计费规则分段；赠送额度消耗仍单列。
- 成功请求必须有用量和计费依据。失败/取消请求的原始 usage 可以未知，但必须另有供应商费用或可证明的未转发记录解释其费用；没有依据保持未知，不能填零。预派发故障的原库 `tokens:null` 仍保留，费用侧另附未转发证明。
- 只有费率乘用量的结果标为**估算金额**；只有账号余额变化标为**账号旁证**。若通道无法提供可归属金额或可隔离账单区间，精确费用项未通过，不能以总账号余额充当单实例账单。

账单尚未出齐时停止新增付费批次，按供应商明示结算窗口等待并记录下一核对时间；等待不新启模型请求。观察本身已经结束时可以事后只补账单，不能据此修改业务执行事实。计费证据不足可报告已知用量和限制，但不关闭成本验收或宣布整体发布通过。

### 6.3 C2 同覆盖费用对照

固定使用第 2 轮的材料定义：12 份各 6,000 字符的材料，每份首次实际读前 4,000 字符，再回查第一份尾部 2,000 字符；保留纠正、禁止修改文件和待办，最终按相同覆盖要求交付。材料、输入、场景和评判均先冻结。

- A 为确定性折叠前的 0.28.9 基线行为，B 为当前封存候选。旧程序使用自己的依赖和隔离新库，只接合成只读材料及隔离渠道；不读取新库，不接真实群数据。P0 核对模型/SDK/提示词和其他差异；无法隔离的差异必须说明为版本比较，不能把全部差额归因于单一折叠算法。
- 先免费核对 A/B 材料与覆盖，收费阶段采用真实模型各执行两次，顺序 A→B、B→A，每次独立会话和数据目录。真实模型自行选择合法调用；不以脚本回答冒充真实调用，不要求固定 14 或 16 次请求。
- 两方使用同一真实模型及参数、供应商/通道和单价口径。供应商缓存不能假定清空或命中；记录每次命中/未命中，把顺序与缓存影响单列。实际账单与统一冻结费率重算的比较值分别展示。
- 四次均须达到相同读取覆盖、禁止事项和准确交付，且无未知金额，才是有效对照。B 的已完成业务读取不得无故重复，重复旧正文输入确有下降；B 两次按同一费率重算的费用合计 **不高于 A 两次合计**，作为本固定样本的费用门槛。降低 20% 是观察目标，不是已证实收益；只下降少量时照实记录。
- 一对缺失、外部失败导致少做业务、材料/目标漂移、费用未知或净费用升高，均不算比较通过。最多在已授权预留内补一对明确失效的样本，并保留首轮结果；不能反复择优取最低费用。

已有字节下降约 35.7%、历史 76 次诊断请求和旧账号余额变化都不作为本次真实费用基线。若无法建立有效 A，C2 标未执行，保留当前测量，先解决基线问题；不直接进入“费用已达标”的最终观察。此处通过也只适用于固定任务，不推算正常日均费用。

## 7. F/O：冻结与同进程两小时观察

### 7.1 冻结条件

P0、P1、S1、S2、C1、C2 均通过后，才建立新的真实观察运行 ID。冻结包及实际加载路径、依赖锁/解析、运行代码摘要、新驱动摘要、判据版本、完整场景卡、脱敏配置、模型路由/实际参数、人格/提示词、正常活动配置、媒体配置和真实平台目标。

若供应商仅给动态别名而没有可固定版本，记录执行前后可见的模型元数据、返回标识及时间；不能伪造固定权重版本。可见版本发生变化则原语义结果不能直接继承，重新判断门槛。官方模型目录可以提供能力和窗口等元数据，但字段可能缺省。[模型目录接口说明](https://api-docs.deepseek.com/api/list-models/)

对原封存运行 `candidate:verify`。验收部署副本若绑定了本机路径，单独记录与原包的允许差异；不能把它的配置改动算作原包未变。冷启动、停止/重启及进程退出恢复放在 T0 之前或本轮结束之后，不能拼入连续时长。已有本地新装证据内容未变时不为计时重复付费业务。

T0 是**本轮实际验收进程完成就绪和加载核对后**的时间。用单调时间测量持续时长，同时保存 UTC 时间；记录 PID、操作系统进程创建时间和实例 ID，防止 PID 复用。观察器不能只跟随配置文件中的旧状态。

### 7.3 故障与等待纪律

故障装置在 T0 前安装并冻结，仅在预定请求/阶段生效，不能中途换模型地址、密钥或重启 Host。优先在验收代理的转发前阻断一小段预定请求，覆盖既有重试后确实进入待恢复状态；保存未转发证明，不花钱制造无意义的真实 500。恢复后必须由同一路由完成真实业务调用和交付。

注入故障本身是预期步骤；未能保存进度、无模型故障通知仍依赖模型、恢复后重做已完成读取、探测成功但业务仍失败却宣称完成，才属于失败。明确区分业务续办的新 Run 与同成果的交付续办；未知发送不自动重发。

等待读取实际阶段、进度和既有 deadline；使用 `wait.ts` 的阶段期限逻辑，不再用统一 300 秒杀死仍合法进行的任务。观察窗口结束不自动宣称任务完成；任务合法进行且额度已预留时继续等待。若因验收预算或执行窗口终止，保存未完成结果，不伪装业务超时或降低验收目标。

### 7.4 连续性与通过标准

- 每 30 秒采集一次不调用模型的进程/就绪/业务摘要，按事件记录任务、回执和费用变化。连续两次未取得证据先诊断；若连续 90 秒没有可独立核验的当次进程证据，记录观测断档，本轮不认定连续性通过，不能事后填心跳。
- PID/创建时间/实例 ID 相同，程序、模型设置和冻结的关键配置未漂移，持续时长不少于两小时。场景要求的计划修订、意图更新、来源撤回和一次性故障开关属于**预先冻结的业务输入**，不是允许任意改基础配置。
- O1–O8 及 R01—R10 的必需部分全部有本轮证据；交付既有发送器回执，也有本轮收端可核对记录。调用受理、登录通过、进程存在或模块加载不单独算成功。
- 撤权、取消、未知副作用、去重和目标隔离无违规；至少一次故障确实走到受影响的业务阶段恢复并交付；O7 后段新任务通过。正确停止/拒绝的负例不能被要求继续外发。
- C1 同样用于本轮所有请求。没有未解释额外调用，未知费用不算零；账单延迟则费用结论保持待核对，不用余额强行结案。
- 实际必需场景失败时立即保存证据并停止本轮，不为了凑两小时空等。短暂可恢复故障若依预定路径恢复不机械判整轮失败；持续服务不可用仅证明退避/保护，业务验收未完成。
- 进程重启、关键内容变化或观察断档后，本轮时长不与新一轮相加。运行或提示词修复需要新候选；单纯文档修正不使有效原始证据自动失效，审计修正另记版本。
