# 大肥鱼开发迭代与验收流程讨论稿

日期：2026-11-07。依据 [多轮迭代复盘](../results/iteration-review-20261107.md)。状态：讨论稿，尚未实施；不代表用户已经同意所有新验收标准或成本目标。

## 1. 本次调整的目标

每轮围绕一条能从用户输入走到最终交付的业务流程，形成可复现的问题、有限的改动、明确的结果和可解释的费用。保留已有有效实现，优先统一跨模块的规则和证据。每次修复都能回答：解决了哪个失败、哪些相邻行为仍正确、实际减少了什么工作、还有什么不能证明。

沿用边界：本地开发和测试；服务器保持停止，用户检查通过后再部署；真实 QQ 外发只到主人私聊，群聊与入站使用隔离回放；不采用子代理改造；上下文最大容量保持 1,000,000 token，不增加任务总 token 或总步骤硬上限。已有外部接口超时、取消、权限和发送回执保护继续生效。讨论阶段不改运行代码或启动真实模型测试。

## 2. 先建立业务要求与证据的对应关系

为每条需求保存一张简短记录，包含：原始诉求、允许的解释、必须保持的条件、成功证据、合理的暂停/部分完成、明确失败、对应测试和当前状态。完成条件在实施前确定，测试失败时不能为取得通过而临时改写。

| 代表性诉求 | 必须保持 | 完成证据 | 不能作为完成证据 |
| --- | --- | --- | --- |
| 把已有巡视改成每两分钟 | 原计划 ID、群范围、消息水位；当前主人授权有效 | 原 ID 上版本增加，读回周期和静默设置，设置任务结束；实际巡视另有回执 | 取消旧计划再建一个；在设置任务内一直等待后台 |
| 通过 DSH 检查消息问题 | 原任务承接；只读范围；推断与观察分开 | 实际工具调用和结果、足以支持结论的材料、最终说明及发送回执 | 只列工具目录；只有 completed；从空缓存推断消息从未到达 |
| 看指定 B站视频后分享 | 账号和接口范围正确；已读材料复用 | 字幕/画面/音轨各自记录实际覆盖，最终表述与覆盖一致，分享有回执 | 登录通过；只有视频资料；采样冒充完整音视频观看 |
| 主人私聊查询群消息 | 主人可跨获准群查询，各群之间隔离 | 查询、上下文、报告和发送四个阶段的范围均正确 | 只证明查询 API 返回群消息 |
| 故障恢复后继续原任务 | 同一 Task；原进度；已确认发送不重发 | 受影响阶段实际成功、补齐缺口、结果交付 | 一次轻量探测成功；重新创建不相关任务 |

这些例子扩展为稳定的需求清单，沿用已有测试，补齐缺失证据；不以测试条数代替需求覆盖率。

任务目标与交付分别记录：目标可以是达成、部分达成、等待恢复、取消；交付可以是待生成、待发送、部分确认、全部确认、回执未知。对用户展示的进度从现有真实记录生成。配置类任务以保存并读回为目标，后台首次执行是另一项事实。

## 3. 分轮实施与退出条件

| 轮次 | 范围与产物 | 进入下一轮的条件 |
| --- | --- | --- |
| 第 0 轮：让验收可复现 | 将完整驱动、审计和必要校准程序脱敏、参数化并纳入版本管理；固定需求清单、模型/配置摘要与基线；整理已知失败样本 | 新的本地验收目录可运行；错误版本、旧结果、遗漏场景、未知发送等会被正确拒绝；有效结果不会被错误超时或函数名匹配误拒 |
| 第 1 轮：任务承接到交付 | 围绕巡视修订和 DSH 诊断两条流程，核对身份、任务意图、计划、等待条件、工具回执、材料与发送；修复明确缺口 | new/amend/取消/恢复分支有确定性回归；真实局部样本证明模型能完成下一步，保留任务和计划身份；配置任务无自等待 |
| 第 2 轮：长任务与上下文成本 | 已读材料可回查、按步骤组织上下文、按阶段提供工具、缩小源码查询范围；统一记录业务与验收用量 | 固定样本的关键事实、否定、最新纠正、授权与待办不丢；重复正文和无效调用减少；缓存变化及未知用量解释完整 |
| 第 3 轮：恢复、报告与主动分享 | 同任务继续、故障范围恢复、主人插话后续办、去重分享；核验同时覆盖漏检与误拒 | 故障到交付的组合测试通过；轻量探测与业务恢复分开；报告修订复用证据；已确认消息不重复、未知回执不冒充成功 |
| 第 4 轮：冻结候选并发布验收 | 独立发布包、安装与回退检查、原始对话全过程和同进程两小时、费用对账、文档 | 必需场景及最终交付全部满足，过程和用量可核对；限制单列；用户检查后再进入服务器部署 |

第 1 轮应优先保留当前已经验证有效的状态与授权实现，不为“统一”另建一套并行业务状态。共同结构只有在真实重复或明确不一致时才抽取。核验错误在所属流程内修复，不把所有语义问题留到最后一轮。

每轮拆成有限工作项，每项只承诺一个可验证的行为变化。跨多个模块是允许的，但相关契约、调用方、界面和测试一起完成。无关整理、新能力和主动性风格调整放入后续清单，避免一次修复持续扩展。

## 4. 每个工作项的执行顺序

1. **复现并分类。** 保留输入、实际版本、触发顺序、期望和实际结果；先判断业务代码、模型判断、外部调用还是验收器出错。原因不明时标记待定位，不先按 500 等状态码免责。
2. **确定验收。** 使用实际失败材料建立最小复现，并加最接近的正确对照。状态修改覆盖相邻分支，语义修改同时覆盖漏检与误拒。
3. **实施与局部验证。** 修改必要范围，核对接口回执和错误后的下一步。涉及资料读取的修复尽量回放已有响应；涉及最终报告的修复复用同一证据包。
4. **真实局部复验。** 只有程序测试无法证明的模型行为或平台路径才使用真实调用。先声明要解决的一个不确定点，完成即结束该样本，不重复整段业务。
5. **提交与记录。** 记录修复、验证、剩余项及实际用量；契约修改和候选整合执行全量回归，安装/启动变更按仓库要求完成冒烟和独立初始化。一般局部改动先做针对性验证，已通过且内容未变的检查不无故反复执行。

同一失败复现且没有新增信息时，转回最小复现和定位，不通过反复完整试跑等待偶然成功。新失败另建记录，说明是否阻止当前交付；不得无声扩大工作范围或把未完成事项隐藏在“已通过”中。

## 5. 上下文和费用治理

百万容量继续作为技术容量。按任务所需信息组织每次请求，将费用观察与业务容量分开。

| 信息 | 建议处理 |
| --- | --- |
| 当前目标、主人最新纠正、限制、下一步、待办 | 保留在精简工作记录中，以程序中的真实状态为准 |
| 当前步骤需要的材料 | 提供相关片段、来源 ID、覆盖范围和必要上下文 |
| 已完成步骤的长工具正文 | 保留原始归档；工作记录引用已确认事实和回查入口，后续需要时按权限读取 |
| 写入及发送事实 | 程序保存实际回执和未知状态；摘要不能改变它们或诱导重做 |
| 等待、冷却、空队列、同范围故障 | 由现有调度和依赖状态处理，模型收到可理解的原因与恢复条件 |

先评估现有整理能力和来源约束，做小样本验证后再决定配置或实现变更。不能直接打开一个开关就宣称降本，也不能机械截断最近若干条历史。任何折叠都要验证权限撤销、证据过期、部分读取、取消和接续；恢复时无需重新读完已经完成的全部材料。

DSH 查询优先定位必要文件和范围，支持一次取得相关结果；B站按阅读记录补齐缺口。工具集合随任务阶段变化，保留可发现的合法后续入口，避免模型把临时暂停理解为没有能力。

成本报告至少分开：正式实例、确定性测试、真实局部复验、最终观察；并按请求、任务和阶段归属。展示请求数、非缓存输入、缓存输入、输出、未知用量、耗时、实际完成的目标。账号余额变化只作旁证，不当作单实例精确账单。

固定业务样本比较同样的目标和材料覆盖，先离线测量上下文组装，再用少量真实调用核对。压缩可能影响缓存命中，所以不能只看累计 token 下降。具体降幅和费用预警值在基线确认后作为讨论项确定，不在本稿中编造节省承诺，也不新增业务任务总量限制。

开发中的付费复测按批次预估和记账；达到观察预警时说明消耗来源与剩余不确定点，停止没有新诊断价值的重复复测。若以后需要测试账户的硬预算，应由用户单独确定，不能把它混成大肥鱼的隐含能力上限。

## 6. 验收本身需要验证

建议在仓库新增参数化验收入口和脱敏夹具目录，复用现有 `scripts/`、`tests/` 的能力。原始账号、聊天、凭据和运行结果继续保存在本机私有目录；公开部分保留场景、预期、判定逻辑及安全的合成替代内容。

验收结果至少绑定程序修订及内容摘要、验收脚本修订及摘要、配置摘要、模型设置、场景 ID、运行 ID、起止时间和判据版本。未知用量、未执行场景、旧文件和未完成结果不可变成通过。

验收器的反例至少包括：读错版本的源码、只列目录、换了计划 ID、漏掉一个必需输入、拿旧请求回执当新结果、发送回执未知、任务正确完成但驱动错误提前超时。自然语言样本包括错误断言、正确限定、混合真假断言，以及未用于调提示词的少量改写样本。

确定性事实直接核对数据库/工具结果/回执；语义核验负责证据与表述的关系。验收逻辑不应把待测模块返回的 success 原样抄成最终 verdict。人工审查聚焦最终正文及程序难以判定的语义，不能代替可以自动核对的 ID、数量和状态。

已有有界报告修订流程继续复用材料。核验服务失败时保留任务成果和待交付状态，可用确定性的状态通知说明阻塞；不能重新执行整段业务，也不能发送未通过的事实正文。

## 7. 一次冻结候选的两小时验收

进入条件：相关修复已通过确定性回归和必要的真实局部复验；`npm test` 通过；安装/启动改动的冒烟、独立依赖新装及适用的迁移回退已完成；已知阻断缺陷清零；实际模型和受测平台路径可用；程序、配置、模型设置、场景和判据固定。

原始真实对话的完整回放放进这一次观察的前段，同时验证任务承接、实际工具、阅读覆盖、最终正文和交付。无需在冻结前后连续重跑两次相同的昂贵完整故事。前段必需场景失败即保存证据并停止该失败轮次，回到局部定位。

建议安排以下检查点，时间用于安排负载，不成为业务任务的额外总时限：

- 前段：原始对话全过程，包括分条回复、指定视频、群查询、原计划修订和 DSH 实际诊断。
- 中段：隔离注入一次模型或媒体故障及主人插话，验证等待、同任务继续、部分阅读复用和交付；故障类型的详细组合在前置确定性测试覆盖。
- 后段：继续正常配置下的活动观察，安排低频的真实业务检查，核对修订后的计划和恢复后的任务，而非只做健康探测。至少保留一次接近结束时的实际任务结果与送达检查。
- 结束：核对未完成任务、分段发送、模型请求、异常及费用；出具逐项结论。停止/重启恢复测试另行安排，重启前后不拼接成同进程两小时。

保持正常活动频率，记录无新内容、冷却、前台忙、依赖暂停等原因。空队列不应被强迫调用模型；业务检查的合成输入明确标记为验收负载，不拿它推算自然待机费用。

通过条件建议同时包含：连续进程与版本一致、必需业务目标和交付满足、隔离与去重满足、故障恢复确实回到业务阶段、后段业务检查完成、全请求对账。用量未知允许如实记录，但未知请求身份和未解释的额外调用必须定位。

若模型持续不可用，可得到“保护与退避行为通过、业务恢复验收未完成”的结果，不能合并成总体业务通过。一次瞬时错误若按约定恢复且全部检查完成，不必机械认定整个程序失败。缺少有效业务负载的两小时仅能证明有限的运行连续性。

运行代码、模型设置或关键配置改变时，新候选重新计时。判据或驱动修正也必须记录新版本：已有原始证据足够时可以单独重新审计并明确标识，缺少的执行证据不能事后补造；文档文字修正不使未改的程序证据自动失效。

## 8. 提交、发布与清理

开发中采用小提交，逐项记录对应需求和证据；最终发布使用新版本、新目录和独立依赖。实际加载修订必须与验收对象匹配，不能用运行中的旧包验证新代码。

兼容分支按真实需要处理：仍支持的旧数据升级保留显式迁移和测试；没有调用者、测试或兼容职责的旧实现，在确认引用后删除；生成文件通过构建同步。历史证据保留在历史目录，新安装入口只描述当前路径。

最终交付固定包含：本轮范围、修订、逐项通过/失败/未执行、两小时业务与进程证据、用量及未知项、剩余问题、安装/回退说明。本地验收与服务器部署分别记录。用户检查通过后才进入已约定的服务器部署流程。

## 9. 建议本轮讨论确定的取舍

1. **优先顺序：** 先完成验收纳管、任务状态贯通和上下文成本治理，再扩大主动探索或调整主动发言风格。
2. **两小时标准：** 建议加入后段真实业务完成与故障后业务恢复要求；保留进程连续检查，但不再将其单独提升为整体可用性结论。
3. **费用约束：** 建议先用可比较样本建立基线和软预警，保留百万容量及无额外任务总量限制。测试账户硬预算如有需要再单独确定。

本稿提出实施方法与候选标准，不承诺消灭全部模型随机性或外部平台故障。具体每轮时间和真实调用费用，应在该轮工作项及基线明确后估算；两小时观察本身独立安排，不用赶截止替代完整证据。
