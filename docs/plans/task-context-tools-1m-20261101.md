# 任务承接、百万上下文与工具衔接：开发及验收方案

日期：2026-11-01。基线：本地 0.26.2，代码提交 `4ecbe09`，验收文档提交 `6e1f7e0`。现场依据：`docs/checks/local-conversation-review-20261101.md`。

本文是待执行方案，不是开发完成回执。本轮只编写方案，没有修改运行程序、实例配置或部署。

## 1. 本轮目标和约束

最终目标：用户用自然语言提出任务、补充或确认后，大肥鱼保留完整意图，自主选择方法，实际使用 B站与必要的 DSH 能力，形成有依据的汇报，并收到目标 QQ 会话的发送回执。

本轮以用户最新要求为准：

- 上下文最大允许使用 **1,000,000 token**，不再设置项目自定义的较小上下文硬上限或固定压缩门槛。此前关于保留 24k/32k 阅读门槛的建议作废。
- 一百万指单次模型请求的上下文容量，不是整个任务累计计费 token 的上限；连续请求的累计用量可以超过一百万。
- 依模型 API 的实际定义计入输入、工具声明、媒体及输出空间。模型自身的真实窗口和单次输出上限不能由修改配置伪造；若实际模型达不到一百万，验收应明确失败或未满足环境条件。
- 取消“三个视频必须换会话”“八段后必失败”等固定阅读结束规则，不用字节、来源数量或阶段配额重新变相卡小上下文。
- 分页、检索和按需装配继续用于可读性与效率，不能静默丢掉与目标相关的内容，也不能把索引页大小当作任务总容量。
- 仅在本地开发、测试、迁移和部署。服务器不连接、不修改、不重启；不把服务器数据复制到本地实例。不自动推送 GitHub。
- 本轮不开发活跃度，不新增子代理体系。沿用现有主会话与任务执行器，先修复现有链路。
- 保留实例身份、消息来源、权限、凭据隔离、取消和未知效果防重发规则。扩大上下文不是扩大外部操作授权。

用户已提供方向，不应因历史文档中的维护窗口或旧审批状态再次停在部署前。执行本方案时，完成已授权的本地工作；真实 QQ 验收由用户在本机对应的机器人会话发起，程序正常回复该会话。自动回放使用隔离渠道，不伪造生产主人消息。

## 2. 问题与交付物对应关系

| 现场缺陷 | 必须交付的变化 | 不足以通过的结果 |
|---|---|---|
| 原任务的纠正、确认变成新任务，甚至 goal="可以" | 带真实消息来源的任务意图与版本承接 | 只给提示词补一句“联系上下文” |
| 约 29k 开场，32k 阻断，换段后仍失败 | 所有模型阶段统一按真实请求口径使用最高一百万容量 | 只改硬编码 32000，留下 1 MB、48k 或收尾阶段的小门槛 |
| 搜索候选、待理解画面未进入接续状态 | 操作完成后自动保存完整工作进度与有效入口 | 只保存模型主动写的阅读结论 |
| 目录可读，但工作阶段隐藏 DSH 能力 | 可发现、可装配、可执行及其限制分别明确 | 只证明 `dsh_tool_list` 能列名称 |
| 抓图/列字幕轨被说成读懂视频，内部失败要求用户缩题 | 逐步覆盖事实与可执行恢复路径进入反馈 | 只返回更友好的错误文案 |
| 离线测试通过，真实对话不能完成 | 原样对话、真实模型、真实平台及最终回执的全过程验收 | 用脚本模型固定调用顺序替代真实模型决策 |

## 3. 开发一：任务意图与对话承接

### 3.1 保存完整、可追溯的意图

在 Core 保存当前任务的意图快照，至少包含：

| 字段 | 用途 |
|---|---|
| taskId、intentVersion | 同一个用户任务及其修订版本 |
| originalRequest | 原始指令的会话、消息 ID、内容摘要与内容哈希 |
| resolvedGoal | 结合上下文整理后的完整目标，不再等于最新一句话 |
| constraints | 当前有效的对象、题材、时间倾向、交付形式等限制及各自来源 |
| delegatedDecisions | 用户明确交给 Agent 的选择，例如搜索方式、筛选与选片 |
| deliveryTarget | 结果送达的原会话与对应消息关联 |
| amendments | 补充、纠正、确认、取消等原话与应用顺序 |
| acceptedProposal | 被确认的方案版本及其已发送回执；没有时为空 |
| supersedesVersion、sourceStamp | 处理迟到调用、重复消息与来源失效 |

目标解释与工具授权分开。模型可整理目标、选择任务关系；程序核对消息属于当前实例/主人/会话、来源仍有效、版本匹配，并按已有授权策略决定外部动作。模型生成的标题或方案不能自行增加文件写入、发布或其它权限。

### 3.2 明确处理每类新消息

| 消息类型 | 处理规则 |
|---|---|
| 完整新任务 | 建立意图和执行记录，取得真正的受理回执后再回复“已开始” |
| 补充、纠正 | 修订原任务的意图版本；保留仍兼容的原目标和交付要求 |
| “你自己决定” | 更新决策授权范围，继续原目标，不把这句话当作新的观看目标 |
| “可以”“就这样” | 关联当前会话中唯一适用且已送达的方案；承接原任务，不生成裸确认词任务 |
| “进度怎么样” | 返回当前任务的真实状态与覆盖，不隐式创建重试 |
| “继续”“重试” | 根据现有任务、终止原因和持久化工作进度恢复；同一任务可创建新运行，不丢原任务身份 |
| 指定新 BV 号 | 新的明确对象覆盖旧的筛选要求；保留兼容的阅读/汇报要求，记录是替换还是另开任务 |
| 取消 | 停止后续步骤，冻结可恢复进度；迟到结果不能继续驱动旧任务 |

“时间靠前”“养鱼”等需要结合实际上下文解释。没有精确日期时可由 Agent 自主给出合理筛选口径并在结果说明；不能凭空改变用户明确的条件。只有确实存在多个无法唯一关联的任务/方案，才询问，不把正常的省略表达退回给用户重述。

方案确认必须关联用户实际可见的方案。未发送草稿、发送未知的内容不自动当成用户确认对象。任务已经完成后收到“可以”，应回应已完成状态，不再启动重复任务。

### 3.3 并发、幂等与恢复

- 意图解释、任务更新和调度共用来源与版本校验；幂等键包含消息、任务、操作类型和期望版本。
- 用户纠正到达时，停止旧版本继续规划或交付；已确认完成的只读工作保留，在新目标和权限下重新核对后复用。
- 同任务修订不能因 `intentVersion` 改变就把所有有效页面当作从未读取；同时不能跨任务、跨主人继承不相干来源。
- 跨数据库写入不假装原子事务。采用持久化待应用记录、幂等应用和恢复状态，保证不会出现“已回复受理，但任务没有落盘”。
- 已有历史“可以”任务保留原始记录；不批量编造新目标。只有恢复时取得真实关联消息并核对后，才建立新的可审计意图版本。

主要修改：`contracts/src/message-task.ts`、`core/src/execution-coordinator.ts`、`channel-qq/src/tasks.ts`、`memory/src/task-repository-adapter.ts`、`core/src/runtime-store.ts`，以及任务状态和管理界面的对应显示。

## 4. 开发二：统一百万上下文策略

### 4.1 统一容量声明，消除分散硬编码

安装设置、Host 配置、Core、普通聊天、任务、接续、结果整理与核验共用一个容量声明，公开设置名称统一为 `contextCapacity.maxTokens`，本地目标值为 `1000000`。管理中心显示配置值、模型真实能力、当前有效值及计量方法。

旧 `contextBudget` 中混合的请求字节、检索展示和区域分页设置拆分：检索/展示参数保留明确含义；项目附加请求总容量门槛移除。配置转换显式处理旧字段，不能旧值悄悄覆盖新值；不能产生两套并行生效的容量配置。

若 API 的输入和输出共用窗口，校验关系为：

`实际投影后的输入 + 本次请求实际输出额度 ≤ min(1,000,000, 模型真实窗口)`

按平台真实协议处理输出额度，不能无条件把“模型允许的最大输出”整块扣除，也不能沿用阶段里写死的 8,192 当成所有场景的约束。结合本次用途、请求输入、剩余窗口和提供方输出上限确定当次输出额度；不能为了固定预留 256k 输出而静默丢掉合法输入。最终 QQ 文案保持正常聊天长度，不因上下文变大就输出巨量正文。

### 4.2 统一计量对象

1. 使用 DSH SDK 实际工具历史、消息和媒体投影后的请求计算；不把本地 `source.sections`、账本哈希和重复工具快照当作模型输入。
2. 实际投影、审计存储、计费累计分别记账，不复用同一个 bytes 数字代表三件事。
3. 优先使用模型对应的可靠计数器。没有精确计数能力时标注估算方法与误差，用平台回执校准；不能再把 `bytes / 3` 冒充精确容量并提前判死合法请求。
4. 保留 SDK 对历史工具声明的正确处理；不能为了减少数字无条件删掉 toolHistory，破坏历史调用语义。
5. 媒体按模型/SDK 的真实计量计算，图片文件字节或 base64 长度不能直接冒充 token。
6. 平台实际拒绝容量时，保存当前状态，针对容量做整理/接续；普通模型中断、网络错误不得一律归类为上下文超限。

### 4.3 需要移除或替换的现有限制

| 当前实现 | 本轮要求 |
|---|---|
| `segment-budget.ts` 的 24k/32k，以及 schema 的较小最大值 | 移除阅读专用硬容量，合并到统一容量策略；无其它调用后删除旧模块及旧测试 |
| `native-runtime.ts` 首轮“+1000”、软阈值“硬上限-1” | 删除这种拒绝逻辑；收尾依据真实剩余空间和正在执行的步骤，不设置新的固定小门槛 |
| 安装器固定 `compactionInputTokens:48000` | 取消固定 48k 强制压缩，按真实窗口和待处理材料决定是否整理 |
| 全请求 1 MB、schema 最大 2 MB | 不作为模型上下文准入条件；串行化与传输能够承载合法百万级请求，按实际协议/系统能力报告故障 |
| 受控上下文 16 KB 总额及必需区域的小额字节门槛 | 改为统一总窗口内的选择、分块与引用机制；不得因旧区域上限拒绝整个任务或静默丢掉必要资料 |
| 独立结果整理、反馈、复核中的较小容量门槛 | 输入容量使用同一声明；输出格式和必要字段校验不冒充上下文容量 |
| 三个视频强制换段、八段终止 | 移除固定计数终止；保存进度可按步骤发生，任务结束由目标状态决定 |
| 继承来源最多 512 项 | 使用持久化、可分页核验的来源集合引用，不因来源数量较多直接终止合法任务 |
| 固定十分钟的隐式任务总期限 | 不用它替代上下文上限。调度时片到期可持久化并继续；用户明确时限仍必须尊重 |

同时核对 DSH SDK 的自动压缩默认值；不能删除显式 48k 后又回落到另一个较小默认阈值。开发阶段产出完整限制清单，逐项注明属于模型容量、单页协议、系统资源、网络等待还是授权检查，并证明没有其它固定容量旁路仍在截断任务。

单次网络/进程操作的超时、用户取消和服务退出继续有效，用于取消真正失联的操作。区分百万输入的首 token 等待、输出流中途空闲和任务总历时；核对现有 40 秒流等待及各阶段超时，不能把合法的大请求预填充或收尾误判为失联。依据实际模型协议和压力测试调整等待策略，并保持随时可取消。运行时发现系统确实不能承载时，给出实际错误及已保存状态；不得静默降回 32k。

每页工具结果、索引和检索片段仍可以保持适当大小，但必须提供可继续读取的入口和明确覆盖。超大结果先保存再返回引用；不能整份变成 null，不能因一页大小限制直接宣称“能力没有加载”。单对象格式校验不是新的任务总容量限制。

### 4.4 长任务保留工作连续性

- 工作状态在每个步骤后保存，不以“上下文快满”作为唯一保存时机。
- 信息仍相关、请求仍在真实窗口内时可继续使用，不因达到 32k/48k 或三个视频提前中止。
- 接近真实容量时，先保存目标、来源、判断、已完成项和下一步，再整理或创建接续会话。
- 检查点存储不依赖必须再调用一次大模型才能完成；必要时程序可以保存结构化状态。
- 新段先装入完整意图和当前未完成步骤，再按需恢复来源；不重灌全部旧会话、旧工具定义与待反思提醒。
- 判断“无进展”依据同一版本/参数/游标反复得到同一结果，不依据简单调用总次数。发现循环后应改变策略或报告具体阻碍，不无限重放。

主要修改：`contracts/src/context.ts`、`contracts/src/host-config.ts`、`plugin/src/settings.ts`、`plugin/src/installation.ts`、`host/src/inline-model.ts`、`core/src/context-plan.ts`、`context-runtime.ts`、`context-snapshots.ts`、`native-runtime.ts`、`execution-frame.ts`、`execution-coordinator.ts`、`phase-stream.ts`、`task-review.ts`、`target-renderer.ts` 及相关来源集合实现。

## 5. 开发三：贯通 B站读取和工作记录

### 5.1 明确分工

Agent 决定搜索方向、筛选条件、选哪个视频、哪些内容值得深入和如何表达。程序负责解析稳定标识、分页、资源准备、工具之间的引用衔接、真实覆盖及恢复。

实现一个可从原子工具和组合读取入口共用的工作记录服务，避免两条互不一致的路径。组合入口不预写结论，不另起规划模型。

### 5.2 保存整个工作过程

| 阶段 | 持久化内容 | 接续时的正确动作 |
|---|---|---|
| 搜索 | 关键词、排序、已读页、候选及来源、排除理由 | 继续比较已有候选，不无理由重新搜第一页 |
| 选择 | 选中 BV、选择依据、当前目标与计划 | 继续这条视频；若换片，记录理由 |
| 元数据 | videoPageId、aid、cid、分 P、时长 | 自动提供后续工具需要的标识 |
| 字幕 | 轨道状态、已取正文、已曝光区间、nextOffset、覆盖缺口 | 列轨后读正文；分页中断后从正确位置继续 |
| 画面 | 采样点、source、有效期、获取结果、视觉理解结果及引用 | 图片已获取但未理解时继续视觉工具，而不是再次截图 |
| 评论 | 页、游标、已读 ID、必要楼中楼、覆盖 | 继续下一页或结束当前样本，不重复读同页 |
| 判断 | 阶段结论、依据、未解决问题、后续动作 | 保留判断与不确定性，不把判断当平台事实 |
| 汇报 | 候选正文、核验结果、交付状态、每条 QQ 回执 | 整理/核验/交付逐步继续，不重复发送 |

至少区分资源已获取、已暴露给模型、已完成内容理解三个状态。字段由实际回执和来源证明更新，不能接受模型自报“我已经看了”就置位。跨库状态通过来源引用核对，不在媒体分析尚未成功时提前标记完成。

工作视图保留当前步骤和可继续读取的入口，全文仍在原库中；来源失效、凭据变化、视频改变或资源过期时重新核对，只补做失效的步骤。判断记录与程序工作记录分开，不能依赖模型调用 `bili_reading_save` 才保留搜索进展。

### 5.3 正常阅读路径

1. 自选任务：结合上下文搜索，基于返回的相关性、发布时间和热度选择一条；指定 BV 时直接定位。
2. 取得分 P 与内容来源；有可用字幕时列轨后实际读取正文，不把轨道列表当文字内容。
3. 按阅读目标准备代表性画面，批量交给现有视觉读取。若视觉是理解该视频的必要条件且不可用，标明缺口并尝试当前支持的替代方式。
4. 在需要声音信息、无字幕或字幕不足时使用现有音频链路；不把字幕阅读声称为听过音轨。
5. 读取与用户要求相符的评论样本，区分视频作者观点、评论者观点和 Agent 自己的判断。
6. 评估信息是否足够回答目标；足够就汇报，不机械穷尽评论或为了凑流程调用所有工具。

辅助入口返回本轮进展、覆盖、下一步和来源引用。原子工具仍可用于精细控制；它们必须更新同一份工作状态。没有明确需求时不把读视频升级成开发插件或修改宿主。

主要修改：`bilibili/src/service.ts`、`reading-resume.ts`、`reading-context.ts`、`reading-facts.ts`、`store.ts`、`media.ts`，及 `media` 的观察/理解回执、相关共享契约。

## 6. 开发四：DSH 能力发现、装配与调用

### 6.1 分开显示能力状态

统一描述已配置、提供方在线、目录版本、当前是否装入、当前任务是否获授权、外部依赖是否已验证。每个不可用状态带明确原因，不再同时给出“有授权/不可用/空目录/无错误码”而要求模型猜测。

只读能力查询在普通聊天和任务阶段均可用，包括 B站阅读阶段。阶段未装载必须显示为“未装载/可申请装载”，不能显示为插件不存在。目录分页和单项参数查询保留。

### 6.2 按需装配，不扩大执行授权

- 常驻简短能力索引；搜索、视频阅读、媒体理解、宿主只读操作等根据当前步骤装配所需工具。
- Agent 可以在任务内选择所需工具组。Core 按真实任务权限和提供方版本核对，注册后才返回可调用名称与参数。
- 工具效果分类由 Host 的可信声明/映射核对，不能因为模型说“这是只读”就允许执行。
- B站阶段不再硬性禁止发现宿主能力；但观看任务不能因发现了 shell 就自动获得改代码、改配置权限。
- 目录版本变化重新查询并核对参数；不能用失效 schema 执行。结果未知时先查已保存回执，不重新触发可能已生效的动作。
- 按需装配用于效率与选用准确度，不设置“只能看见 N 个工具”的永久能力上限；未显示的能力应可继续发现。

主要修改：`core/src/harness-runtime.ts`、`reading-stage.ts`、`native-runtime.ts`、`execution-coordinator.ts`、`host/src/dsh-tools.ts`、`dsh-catalog-view.ts`、`plugin/src/bridge-parent.ts`、`bridge-client.ts` 及能力状态契约。

## 7. 开发五：进度、失败恢复与最终交付

任务进度和失败通知必须同时使用完整任务意图、最新纠正、当前工作步骤、真实覆盖、错误归类、已尝试恢复及下一步。

| 情况 | 正确处理 |
|---|---|
| 普通用户问进度 | 回答已做、未做和正在做；不隐式重试，也不引入不相干历史任务 |
| 字幕只有轨道 | 说发现字幕轨，继续读取正文，不能说字幕已看完 |
| 只有抓图回执 | 说已获取采样画面，继续理解，不能说已经看懂画面 |
| 内部容量/配置问题 | 程序整理或恢复；不能声称用户要求太宽或“缩小一定能解决” |
| 平台受限、凭据失效 | 按实际错误说明可继续和不能继续的部分，保留真实暂停状态 |
| 用户已委托筛选 | Agent 在授权范围内自己决定，不重复要求用户挑题材或视频 |
| 确实缺少必要信息或权限 | 只询问具体缺口，并保留已完成工作 |
| 已承诺继续 | 必须有实际排队/恢复记录；没有记录就不能说已经安排 |

完成状态分为工作已完成、汇报已生成/核验、交付已确认；不能只用一个 completed 混合表达。最终汇报对应具体视频，包含内容概括、评论观察、必要依据和覆盖限制。自选场景还应说明选择依据；这些是语义验收要求，不强迫每次采用相同报告模板。逐项核对目标交付物与真实来源，模型自报“完成”不能代替内容核验。QQ 使用现有消息序列和逐条回执，未知发送不自动重发。

主要修改：`core/src/native-task-delivery.ts`、`target-renderer.ts`、`conversation-coordinator.ts`、任务状态查询、管理中心任务详情，以及工作覆盖和交付契约。

## 10. 验收环境与执行层次

### L1：确定性回归与故障注入

使用真实 Core、SDK、工具注册、来源账本及交付逻辑，平台和模型响应可模拟。固定时钟、目录版本、分页与故障点；用于验证状态、权限、幂等和恢复规则。脚本模型只在这一层作为测试工具，不代表真实 Agent 决策通过。

### L2：生产装配回放

使用真实发布包、当前本机模型路由和完整工具/提示装配，隔离数据目录及模拟 OneBot。原样输入对话并观察自由选择工具的过程；不按调用次数返回预写答案，不阉割工具或人格来降低容量。不复制生产凭据到发布包，使用外置已授权的本机配置引用。

### L3：本机真实对话

由用户在本机大肥鱼对应 QQ 会话发出真实消息；后台只读采集任务、工具、上下文和交付记录。实际使用本机模型、Cookie/浏览器与媒体能力，最终答复由该机器人送回原会话。服务器仍不参与。

本轮测试不使用电脑操控脚本；诊断、部署和采证使用 CLI、后端 API、日志与数据库只读接口。

## 12. 本次真实对话的全过程验收脚本

### 场景 A：自主选片，承接纠正与确认

按本次真实原话测试：

1. “找一个有一定热度、时间靠前的关于【养鱼】或【我想给她完整的一生】类似的视频看看，看完后再跟我汇报一下”
2. “你应该有自己的决断，我给你布置的任务只是找到一个视频去看，如何找、找到后如何过滤和选择，应该由你自己决定”
3. “进度怎么样了”
4. 在对应方案可见后：“可以”

L1/L2 在受理后、搜索后、准备交付前分别安排后续消息，覆盖不同到达顺序。L3 不要求模型说出某句固定话，也不为等待后续测试消息故意拖延任务：若已提前完成，“可以”应只关联完成状态。

必须观察到：任务意图保留原目标和最新约束；Agent 自主筛选并确定视频；读取内容、必要画面和评论；生成有来源的汇报并送达；当前任务没有裸确认词目标，也没有因为正常筛选而要求用户替它选视频。

### 场景 B：指定视频直达完整汇报

输入：“BV1JPx16tEWG 看看这条视频”。

以该短片为固定样本，验证实际取得可用字幕正文及其完整可读范围，代表性采样画面真正进入视觉理解，至少读取一页评论；最终说明视频主题、主要内容和评论区观点，区分作者、评论和自身判断。

画面可以明确标为采样，不能声称连续观看所有画面；没有处理音轨就不声称听过。若平台样本在验收时不可用，保留原样本失败证据，再另记替代样本，不能把替代样本冒充原样本通过。

### 场景 C：DSH 工具实际参与完成任务

在本机验收目录准备不含敏感信息的说明文件，写入样本 BV 号和汇报要求。用户要求大肥鱼发现可用的本机读取工具，读取该文件，再按文件指定的视频完成汇报。

必须出现真实 DSH 目录查询/参数核对、获授权的文件读取、B站工具组装配、内容理解和最终 QQ 回执。说明文件只是任务材料，不能作为扩大权限的指令来源。

场景 A/B 各进行两次独立完整运行，保留全部失败与重跑记录；不能挑一次成功覆盖其它失败。C 至少有一次完整真实模型运行。L3 的用户消息与机器人回执要能对应到同一任务和最终结果。

## 13. 百万上下文专项验收

容量支持与长输入理解分别验收，不能由一个数字代替另一项。

1. **本地精确边界测试**：使用同一计量和投影模块构造跨越旧门槛、接近百万、刚好允许与真实超限的请求；模拟服务确认准入与序列化，没有大模型调用成本。
2. **真实长请求**：在隔离验收会话中发送明显跨越旧门槛的有效请求，验证工具调用、结果处理和最终回答连续完成。
3. **真实接近百万的一次专项运行**：使用非敏感合成材料，按实际计数器与当次输出额度构造接近有效上限的合法输入。材料开头、中间、末尾放置可核对的任务事实，要求检索、关联并完成一次工具步骤和最终汇报。记录平台报告的实际用量、耗时和结果，不在生产 QQ 中灌入巨量测试正文。
4. 输出允许的容量、实际发送规模、平台接受情况和理解质量分开记录。未执行真实接近百万运行时，只能写“本地边界验证通过，真实百万压力未验收”；不能写“百万实测通过”。
5. 如果准确 tokenizer 或平台计数接口不可用，标明估计而不是编造精确百万规模；依据平台实收用量确认覆盖。项目代码不得以未校准的估计再次设置较小的隐形限制。

专项压力样本集中运行一次，不让每项回归都重复发送百万输入；这是验收安排，不是运行时上下文配额。
